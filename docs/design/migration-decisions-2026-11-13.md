# GCSP migration decisions — 13 November 2026

Gary asked for all design documents to reflect the migration refinement. This record consolidates those decisions and explains how to read the updated design set. The [canonical HLD](gcsp-high-level-design.md), [FUCQ-434 replacement contracts](../gcsp/migration-replacement-contracts-2026-11-13.md) and [frozen capability/visual/artifact baseline](../gcsp/migration-baseline-2026-11-13.md) supply the engineering detail. A target diagram or updated document does not establish implementation, configured services, passing acceptance or live BMW integration.

## Agreed design

| Area | Decision |
| --- | --- |
| Scope and baseline | GCSP only. Preserve implemented capabilities, business outcomes and visual design at **`e44ed08a9674d8bf0fe6de2e7195ec3e2d775d38`** on `gcsp-poc-dev`, except the identity changes below. Later product requests and unfinished backlog stay separate. Preserve Used Cars frontend, Node API and shared consumers. |
| Frontend | Angular **21** owns screens, routing and presentation state in `apps/gcsp-web/`. Legacy custom elements may help during migration; permanent legacy screen/controller wrappers do not meet completion. Reuse/adapt shared components and tokens. |
| Backend | Java **21**, Quarkus **3.x** in `services/gcsp-api/` owns GCSP APIs, application state, business calculations, inference and runtime jobs. Deployed GCSP does not invoke Node business code. Offline data preparation/generation/training may remain JavaScript with versioned output artifacts. |
| Request path | Static Angular → separately deployed Java API → repositories and dedicated external adapters. `/gcsp/` belongs to the static router; `/api/gcsp/v1` belongs to JSON/binary APIs. Angular API clients and backend upstream adapters are different boundaries. OIDC redirects and approved static imagery are explicit exceptions to the application-data path. |
| Build and configuration | One repository, one Render blueprint, independently buildable/releasable frontend and API. Deployment supplies **public** API/OIDC/environment settings without recompiling Angular; verify unchanged compiled bundle hashes. No credentials, mail keys, database secrets or client secret in static output. |
| Hosting | Retain Render; Cloudflare was rejected. Prefer existing Render hostnames and prove HTTPS, CORS/preflights, OIDC callbacks, deep links and email returns. A custom domain is a fallback if actual hosting/provider constraints require it, not a chosen prerequisite. Minimize cost; no paid tier/domain is selected. [Dated cost options](../gcsp/angular-java-story-refinement-2026-11-13.md#interim-render-cost-options--checked-13-november-2026) are planning evidence, not a capacity guarantee. |
| Environment | Gary creates a separate dev environment from `gcsp-poc-dev`, with its **own PostgreSQL database**, through the shared blueprint. Confirm actual connection/reset isolation from the running `gcsp-poc` environment. No dev reset or migration acts on the running app's database. |
| Authentication | Interchangeable OAuth 2.0 / OIDC integration proved through a real local/test-provider browser flow. Angular sends JWT **access** tokens using `Authorization: Bearer`. Java validates signature, issuer, audience and lifetime, then role/resource ownership. Corporate BMW activation follows with access/contracts; BMW SSO is not proved by substitute login. |
| Roles | Employees and Greg act only through their respective logins. Presenter has a dedicated login/role for clock, releases, scenarios, resets, fault/retry controls and authorized read-only inspection including outbox/comparisons. No principal switching, employee commands or Greg business commands under presenter identity. Greg owns comparison start/rerun and planning/submission. Scenario-driven simulation remains a backend control, not impersonation. |
| Offer entry and auth recovery | New offer links require sign-in, return to the requested offer and employee ownership. An opaque ID/link does not grant authority. Renew authentication where supported; otherwise sign in and return to the authorized page/saved progress. Never automatically submit an unfinished order after recovery. Sign-out clears application authentication/private state and ends the provider session where supported, permitting account change. |
| Compatibility | No legacy GCSP URL/API-consumer compatibility is required. Document replacement routes and update shared launcher/brand handoffs. Keep Used Cars consumers compatible. Legacy cookies, shared passwords, link-only offer sessions and same-origin Node page gates are baseline evidence, not target authority. |
| Adapters | Reuse established ports and select providers at deployment/startup; runtime presenter switching is unnecessary. Keep transport, upstream shape/auth and scenario preparation out of core business logic. Dedicated boundaries follow coherent upstream capabilities, not one adapter per field. A provider must explicitly refuse unsupported actions; no silent synthetic fallback. |
| Business authority | Backend-owned preferences, calculations, policy and persistence remain application responsibilities. Preserve one canonical PolicyService, exact `orderUuid` versus shared `configurationId` versus VIN, source/provenance, pinned quote/policy versions, hard and unknown gates, deterministic ties, exclusive custody, durable receipts and pending/retry/reconciliation semantics. Logical modules are not a mandate for microservices. |
| Numerical parity | Agree explicit calculation tolerances while preserving displayed values, eligibility, ranking, tie-breaks and allocation/order outcomes. Tolerance is not permission to change decisions. |
| Retained/reset data | Keep source corpus, reference/policy versions, reusable trained models and agreed baseline comparison artifacts. Legacy employee/scenario state, sessions, offers/orders, old offer links and operational learning/comparison history may reset at the switch. Replacement-app state, receipts, pending work and **new** offer links survive normal compatible releases/restarts. |
| Substitution proof | Working test OIDC and realistic local substitutes first; complete remote substitution and full transactional proof before final acceptance. Missing remote offer acceptance/decline is separately scoped in **FUCQ-467**; FUCQ-106's delivered exclusions are retained. BMW source/API activation awaits actual access and capability evidence. |
| Email | Both connected proofs require actual delivery through the configured adapter to an agreed test recipient and the signed-in owned-offer return journey. Captured outbox and provider acceptance alone are insufficient. Simulations/comparisons retain captured notifications and do not send real mail. |
| Experience | Preserve the frozen implementation and approved visual references, shared component language, concise copy, imagery, responsive states, Safari/private browsing, keyboard/focus, accessibility and CSP requirements. No new product redesign, on-screen demo disclaimers or permanent legacy controller ownership. Unapproved Greg concepts are not a new migration baseline. |
| Standards | Confirmed constraints are Angular 21, Java 21, Quarkus 3.x, bearer JWT and the retained experience/deployment requirements. Gary will supply further BMW standards; record and reconcile them in the relevant Story. Do not invent BMW library/container/claims/service compliance. |
| Workload and review | No fixed deadline. Support current scenario/comparison sizes and a few simultaneous demo users; measure hosted capacity before choosing the cheapest suitable resources. Continuous engineering checks, rendered inspection and coherent commits apply. No interim human checkpoints: Gary reviews the complete hosted dev build at the end. |
| Final switch | Gary merges into `gcsp-poc`, triggering a replacement Render build; downtime and immediate retirement of the old deployment are acceptable. No retained old deployment, draining or deployment rollback rehearsal. PostgreSQL transaction rollback, uncertainty recovery and ordinary app persistence still apply. This documentation update does not perform that merge or any provisioning/deployment/reset/send. |

## Priority and parallel delivery

The combined run includes **four Epics / 66 Stories**: performance **FUCQ-408** (409–425), static/API **FUCQ-431** (434–438), Angular **FUCQ-432** (439–453), Java/adapters **FUCQ-433** (454–482). The [published migration map](../gcsp/angular-java-migration-publication-2026-11-13.md) and [combined kickoff prompt](../gcsp/angular-java-dev-poller-kickoff-2026-11-13.md) identify native issues and execution rules.

1. FUCQ-434 fixes the baseline, API and ownership contracts. Its [baseline](../gcsp/migration-baseline-2026-11-13.md) now records the actual kickoff SHA; earlier future-freeze wording describes the authoring requirement.
2. Angular FUCQ-439 and Java FUCQ-454 can proceed against agreed contracts in separate file lanes. FUCQ-455 proves auth; reconcile persistence design early, before FUCQ-456 and transactional consumers commit to schema/access patterns.
3. After sign-in/account, prioritize **Buddy → real test email → signed-in acceptance → order/status**, using local substitutes. Complete the remaining preserved capabilities, FUCQ-467 remote decisions and FUCQ-481 substitution proof before final hosted acceptance. No human checkpoint blocks this order.
4. Deliver native performance in parallel where actual interfaces, ownership and machine capacity permit. Native chains: **417 → 418**, **419 → 420**, **422 → 423**, with **424 requiring 422 and 423**. 421 and 425 are independent of that write-set chain. Serialize shared files/migrations/merges and heavy validation.
5. FUCQ-408 is fully in this requested run; its authored Node acceptance is not optional or automatically fulfilled by Java. Verify required native paths before retirement. Apply relevant selected-read, freshness, explicit-write, receipt/evidence bounds and computation objectives in Java. Completion of every Node optimization is not a blanket migration gate. Preserve live claims, fixed acceptance and explicit dispositions.

The [database alignment](../gcsp/database-refactor-migration-alignment-2026-11-13.md) gives the detailed mapping. Actual code/interfaces and claims determine technical readiness, not Jira journey-order links alone. A dispatch split is not a permanent file claim or acceptance.

## Reading the design set

- [Design index and refreshed diagram exports](README.md) are the visual entry. Diagram colors describe responsibility/source confidence, not implementation completion.
- [Shared contracts](../gcsp/shared-contracts.md) and capability-specific contracts retain native business semantics and dated evidence, with explicit migration overlays for changed identity, routes and runtime. Read the replacement contract for the v1 API. Do not port legacy authentication/hosting requirements simply because a native test once asserted them.
- [Demo brief](../gcsp/demo-brief.md), [build rules](../gcsp/build-rules.md), [experience contract](../gcsp/experience-quality.md) and [component catalogue](../../COMPONENTS.md) retain their purpose/quality authority with the migration changes incorporated.
- Assessments, reviews, historical handoffs, research, native Story cards/receipts and approved visual mockups remain evidence at their recorded revisions. Notices identify superseded design choices without rewriting delivered acceptance or observations. The pitch deck and source screenshots are historical inputs, not the target architecture.
