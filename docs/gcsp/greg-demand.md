# Greg saved-demand projection · FUCQ-99

`createGregDemandService({ repository, policy, clock, identity }).readDemand(context)` supplies the backend-only dashboard contract. `createGregRoutes(service)` registers `GET /api/gcsp/greg/demand`, requiring the trusted Greg role; no query selector or browser identity/run override is accepted. The response is current-run scoped and derived afresh on each read. Missing composition, policy or evaluation data is unavailable; concurrent input changes produce a refresh conflict. No writes, background process, retail display sample or prediction are involved.

`value` contains `runId`, demo-clock `asOf`, opaque `projectionVersion`, `basis: expressed-saved-demand`, policy/brief/clock versions, `privacy`, `demand`, `holds`, `offers` and `stock`. Counts use `{ count, versions: { brief: [version], policy: [version] } }`. A count at least the policy threshold uses `{ kind: exact, value, label }`; every smaller count, including zero, uses only `{ kind: band, fewerThan: N, label: fewer than N }`. The dashboard must render this label directly and must not infer an exact suppressed value from a band. Bucket counts can overlap: unmet gates identify all actual failing/unknown gates, and an accepted offer can later be selected. They are not additive populations or satisfaction measures.

Demand takes the latest confirmed brief per employee; historical/draft versions and current-car facts cannot add demand. Paused/off search permission preserves expressed intent without authorising a search or hold. Confirmed non-indifferent body/fuel preferences and confirmed essentials supply the grouping. Optional `essentials.modelLine` expresses an exact model-line requirement through the existing generic essential gate; older briefs remain valid and appear as `unspecified`. Unknown/unconfirmed inputs stay explicit. No desired model is inferred from a current car, a recommendation score or stock. `essentials` retains only the registered requirement field/operator/value/unit/state, counted with its brief/policy versions.

Unmet demand evaluates the complete visible released/held/allocated repository stock through FUCQ-29's shared driver, eligibility, affordability, essential, charging and timing gates. Unavailable exact stock blocks; missing supplied employee facts require confirmation. The employee provider facts come from the existing `employees.contract.manualContext.employeeFacts` location; charging, when explicitly saved, comes from the confirmed brief. Missing supply and invisible supply have distinct gates. Full decisions stay server-side; the projection includes only grouped gate codes and counts. No recommendation display limit limits evaluation. The existing `offer.declinedCar.exclusion` policy blocks an unchanged declined exact car until a relevant confirmed preference/essential change. Pause/resume and confirmation timestamps alone do not count as changed intent; the projection never learns a preference from a decline reason.

Stock groups actual released/held/allocated state by known typed `facts.modelLine`, or the retained eligibility model key's model token. Missing model evidence remains `unconfirmed`. Only available released stock counts as released; held and allocated stock retain their separate actual states. An order request or confirmed future supply is not released stock.

Holds retain recorded total/occupying-state/type counts and brief versions via their quote/offer. Offers made count durable offer records once; accepted/declined/expired/selected reflect actual offer/decision records, with selected allocations also requiring the corresponding allocated hold and exact stock. Typed decline reasons expose only registered preference/essential types and stable protocol categories; free text and unknown reason types become `unclassified`. No names, individual identifiers, trip/usage histories, employee facts, decision free text, candidate snapshots or scores appear. Upstream release/offer/decision capabilities are separate stories; tests write their real repository input shapes rather than assert fabricated production events.

`greg.demand.smallCountThreshold` is a positive integer count read only from PolicyService, with explicit assumed provenance in the canonical seed. Missing/invalid policy fails closed. This is a revisable synthetic demo privacy choice, not verified BMW policy or a claim of formal statistical disclosure protection.

The service changes what the later Greg dashboard can show, so `experience-quality.md`, the supplied header/sidebar/palette references in `screens/README.md`, the Used Cars body direction and `COMPONENTS.md` remain binding. No new screen/component is built here; screenshots would not validate this backend contract. The consuming dashboard must preserve bands, show source/time/version and unknown/error/empty/refresh states, label expressed demand and distinguish observed outcomes from predictions or satisfaction.

Repeatable scenarios are executable in `server/test/gcsp-greg-demand.test.js`: bootstrap a synthetic run, save/confirm a brief, inspect no-stock gates, release an insufficient then sufficient exact car, record a typed decline and selection, and read the changed projection. Also replay a reset and prove the old Greg session is stale and new run has no carried demand; vary only the canonical privacy threshold in an explicit alternative PolicyService source. These tests use real BriefService persistence and repository transitions; they send no messages and contact no operational provider. The later dashboard/manual-scenario story owns click-through UI, while these fixtures define expected response states.
