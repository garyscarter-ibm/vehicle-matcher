# Buddy allocation · FUCQ-96

First bounded service slice on `dev/DEV-2026-11-04-059`. This contract describes an in-process service; FUCQ-92 event composition and FUCQ-100's transactional hold/offer producer remain final integration gates. No public route or screen is introduced.

`createAllocationService({ repository, policy, clock, identity, claim }).allocate(presenterContext, event)` takes an adapter-issued current presenter context and `{ eventId, eventType: 'stock-released' | 'brief-changed', runId, ...sourceVersions }`. Context and policy authority never come from this event. Callers retain the actual source event identity. A reused event ID with changed contents conflicts.

The run reads current confirmed briefs, employee/entitlement records and complete exact stock through TransactionRepository. Unpaused search consent enables evaluation; hold consent additionally enables a claim. Occupying manual/buddy states and allocated/held stock exclude employees, entitlements and exact cars. Only visible `available` stock (or the existing `released` vocabulary) enters FUCQ-29. Existing supplied employee/driver facts, saved charging and exact stock snapshots feed `createEmployeeRecommendationService().recommend()`. Allocation consumes **all** `decisions`, including those beyond the display cap. Unknown gates remain unsuitable. No second matching engine exists.

Current source contracts are `employee.contract.manualContext.employeeFacts`, the employee driver's provenance-bearing `eligible` fact, and exactly one current employee/scheme/slot contract's `contractEndDate`. Missing renewal dates refuse allocation rather than gaining synthetic priority. Stock uses immutable `facts`, scoped `visibility` and `release.availability`. FUCQ-29 requires known `availableFrom` **and** `availableUntil`; a missing source end remains `needs-confirmation`, never an invented expiry.

FUCQ-92's agreed producer receipt is `consumerId: stock-release`, `eventType: stock-released`, `state: completed`, `eventId: trancheId`. Its successful outcome carries `{ kind: 'stock-released', runId, trancheId, windowId, supplyId, tickId, releasedAt, orderUuids, visibleOrderUuids, policyVersion, source }`. Composition maps `trancheId` to allocation `eventId` and retains the event fields and input versions. FUCQ-91 emits `consumerId: brief:changes`, an actual `brief-changed` event in `outcome.value`, and brief/policy input versions. The first slice does not register startup or clock handlers. Presenter tick contexts can use the guarded cohort seam; DemoClock startup uses a backend scope without a session, so unattended startup allocation additionally needs a reviewed trusted service-identity composition. It must not forge presenter roles or mint a cookie to bypass this guard.

## Deterministic policy and exclusions

PolicyService supplies `allocation.tieBreak.rule`, `allocation.tieBreak.seed` and `offer.declinedCar.exclusion`, with coherent policy version and provenance. Unknown/missing rules refuse work. The canonical `renewalDueThenFitThenSeededLottery` comparator orders all eligible employee/car pairs by actual contract end, eligible fit, then SHA-256 of the configured seed/run/employee/exact-car identity. The implemented alternative `fitThenRenewalDueThenSeededLottery` allows a one-entry policy experiment. Stable IDs resolve a hash collision. This is a greedy deterministic assignment under the published rule, not a maximum-total-fit optimiser. Neither input iteration nor mail affects it.

Each exact car and employee/entitlement can succeed once. An unchanged declined exact car is excluded under `untilRelevantConfirmedBriefChange`. Semantic confirmed preference/essential content is compared with the decision's saved brief, ignoring provenance-only changes, pause/resume and equipment array order. A relevant confirmed change permits re-evaluation through the same gates. Expiry and missed mail never enter dislike or priority calculations.

## Claim handoff and replay

`claim.tryClaim(employeeContext, claimInput)` is mandatory. `claimInput` contains `{ runId, eventId, operationId, employeeId, entitlementSlotId, renewalId, orderUuid, quote, expectedVersions, reasons, renewalDue, score, lottery }`. The quote pins exact snapshot, employee facts, terms, evaluated versions, reasons and trade-offs. Expected versions include stock, slot, employee, brief, consent, policy and clock. The port must revalidate current permission, eligibility, essentials, versions and quote validity and atomically create its hold/offer/outbox through the existing shared claim authority. Allocation creates none of these records.

`ok` means the claim is secured; `conflict` or `stale-version` lets allocation consider the employee's next appropriate contender. Any uncertain/unavailable response leaves the run pending, without proceeding to another claim. The stable operation ID binds run/event/employee/exact car. An injected producer **must** replay that ID idempotently, including a crash after its commit and before allocation acknowledgement. It must preserve uncertain claims until reconciliation. Repeated calls with that ID receive the same quote.

The existing `event_receipts` row under `buddy-allocation` stores the trigger digest, source versions, immutable evaluated plan and progress before handoff. A pre-plan source read has its own attempt identity: if evaluation rejects that snapshot, an identical event retry can read repaired source records. The accepted prepare receipt freezes the plan. Each attempt advances by optimistic CAS. Completion records `{ state: 'allocated' | 'no-assignment', runId, event, evaluatedAt, policyVersion, assumptions, inputVersions, assignments, attempts, evaluations }`. `assignments` retain employee/exact-car/quote and grounded reasons. Reopening/replaying a completed event returns its original outcome without calling the producer. A pending replay resumes its saved plan; the claim port checks whether any current versions have changed.

## Trusted cohort identity

`DemoIdentityAdapter.resolveEmployeeContext(controller, employeeId)` is an in-process presenter-only seam. It validates the current adapter-owned controller, canonical configured employee and matching seeded scheme/grade/slot ownership, then issues a frozen adapter-owned employee context. It preserves the controller's expiry and run guard and issues no cookie/session. Derived contexts cannot become presenters, resolve another employee, bypass resource checks or cross a reset. This method has no HTTP endpoint.
