# Buddy allocation · FUCQ-96

In-process allocation service on `dev/DEV-2026-11-04-059`, composed into the shared runtime on 7 November 2026. `createGcspRuntime` builds it with the trusted identity adapter and the FUCQ-100 buddy hold service as its claim port, and server startup registers it at the DemoClock `buddy-allocation` stage. No public route or screen is introduced.

`createAllocationService({ repository, policy, clock, identity, claim }).allocate(presenterContext, event)` takes an adapter-issued current presenter context and `{ eventId, eventType: 'stock-released' | 'brief-changed' | 'buddy-expired' | 'buddy-declined', runId, ...sourceVersions }` (a `buddy-expired` or `buddy-declined` event also carries a non-empty `holdIds`). Context and policy authority never come from this event. Callers retain the actual source event identity. A reused event ID with changed contents conflicts.

The run reads current confirmed briefs, employee/entitlement records and complete exact stock through TransactionRepository. Unpaused search consent enables evaluation; hold consent additionally enables a claim. Occupying manual/buddy states and allocated/held stock exclude employees, entitlements and exact cars. Only visible `available` stock (or the existing `released` vocabulary) enters FUCQ-29. Existing supplied employee/driver facts, saved charging and exact stock snapshots feed `createEmployeeRecommendationService().recommend()`. Allocation consumes **all** `decisions`, including those beyond the display cap. Unknown gates remain unsuitable. No second matching engine exists.

Current source contracts are `employee.contract.manualContext.employeeFacts`, the employee driver's provenance-bearing `eligible` fact, and exactly one current employee/scheme/slot contract's `contractEndDate`. FUCQ-240: a contender without exactly one current contract with a valid `contractEndDate` is left out of buddy contention. Its recorded evaluation carries blocker `renewal-deadline-unknown` (with `currentContracts`, the number of matching current contracts), it never gains a synthetic date and it never fails the batch; every other employee is evaluated and allocated as before. The completed outcome lists `excluded: [{ employeeId, code }]` (absent when nobody is left out), the tick outcome carries `limitations: [{ code, employees }]` (a count, no ids), the employee's activity check carries `limitation`, and both the employee activity and presenter tick screens state it. Slots and briefs have no needed-by date today. Stock uses immutable `facts`, scoped `visibility` and `release.availability`. FUCQ-29 requires known `availableFrom` **and** `availableUntil`; a missing source end remains `needs-confirmation`, never an invented expiry.

FUCQ-92's producer receipt is `consumerId: stock-release`, `eventType: stock-released`, `state: completed`, `eventId: trancheId`. Its successful outcome carries `{ kind: 'stock-released', runId, trancheId, windowId, supplyId, tickId, releasedAt, orderUuids, visibleOrderUuids, policyVersion, source }`. FUCQ-91 emits `consumerId: brief:changes`, an actual `brief-changed` event in `outcome.value`, and brief/policy input versions.

`consumeTriggers(presenterContext)` reads these actual completed successful receipts from the shared run-scoped repository. It retains the complete producer payload, `sourceEventId` and `sourceReceipt = { consumerId, eventId, inputDigest, inputVersions }`. Allocation uses `allocation:<SHA-256([consumerId,eventId])>` as its event ID, preventing equal IDs from different producers from colliding. Events are ordered by source time, consumer ID and source event ID. The source run/type/identity/time must agree; malformed completed sources return `unavailable` with code `allocation-trigger-invalid`. Unrelated, pending and failed producer receipts create no allocation. Changed completed source evidence conflicts with the previously prepared allocation. An uncertain claim stops this scan; the next invocation resumes the saved event/operation/quote before considering later events.

**Hold expiry (FUCQ-227).** FUCQ-100's `buddy-expiry` receipts (`eventType: buddy-expired`, `eventId: holdId`, outcome `{ holdId, orderUuid, expiredAt, ... }`) are a third trigger. `buddyExpiryEvents(runId, receipts)` groups the holds that lapsed at one `expiredAt` into one `buddy-expired` event, `sourceEventId = buddy-expiry:<SHA-256([expiredAt, sorted holdIds])>`, so the buddy-expiry stage's lapses are re-allocated on the same tick, and a repeat tick hydrates the completed event without another claim. Under `offer.expiredHold.reallocation` = `lapsedHoldersSitOutAndNobodyGetsBackACarTheyLetLapse` (read only for this event type), the employees whose holds lapsed do not contend in that allocation, and no expiry allocation offers an employee a car on which they already have a `buddy-expired` hold. So the car goes to a waiting employee rather than straight back to its lapsed holder, and two non-responders cannot pass it back and forth. Everyone competes again at the next release or brief change: an expiry is never a decline and gives no priority. The comparison's buddy route does not replay this trigger; its record says so in `limitations` (see `shared-contracts.md`).

**Decline (FUCQ-233).** FUCQ-106's completed `offer-decisions:events:v1` receipts with `eventType: offer-declined` (outcome `{ event: { eventId, runId, holdId, orderUuid, employeeId, occurredAt, ... } }`) are a fourth trigger. `buddyDeclineEvents(runId, receipts)` makes one `buddy-declined` event per decline, with `holdIds: [holdId]` and the generic `allocation:<SHA-256([consumerId,eventId])>` ID, so the next tick offers the car to another eligible employee and a repeat tick hydrates the completed event without another claim. Under `offer.declinedHold.reallocation` = `declinersSitOutAndTheDeclinedCarStaysExcluded` (read only for this event type), the employee who declined does not contend in that allocation; `offer.declinedCar.exclusion` still keeps that exact car from them in every later allocation until a relevant confirmed brief change. The comparison's buddy route does not replay this trigger either.

Allocation does not invoke the supplied clock transaction helper around its own transactions. Actual same-tick release consumption is proven against the pinned F92 producer; source inputs in that proof remain explicitly synthetic.

`createGcspRuntime` exposes the service as `allocation` and `dependencies.gcspAllocation`; `buildServer` startup calls `register()` after the buddy hold service starts. Allocation then runs on every presenter tick, after `release-pull` and before `outbox-dispatch`. Presenter tick contexts can use the guarded cohort seam; DemoClock startup uses a backend scope without a session, and configured startup stages exclude allocation. Unattended startup allocation additionally needs a reviewed trusted service-identity composition. It must not forge presenter roles or mint a cookie to bypass this guard.

## Deterministic policy and exclusions

PolicyService supplies `allocation.tieBreak.rule`, `allocation.tieBreak.seed` and `offer.declinedCar.exclusion`, with coherent policy version and provenance. Unknown/missing rules refuse work. The canonical `renewalDueThenFitThenSeededLottery` comparator orders all eligible employee/car pairs by actual contract end, eligible fit, then SHA-256 of the configured seed/run/employee/exact-car identity. The implemented alternative `fitThenRenewalDueThenSeededLottery` allows a one-entry policy experiment. Stable IDs resolve a hash collision. This is a greedy deterministic assignment under the published rule, not a maximum-total-fit optimiser. Neither input iteration nor mail affects it.

Each exact car and employee/entitlement can succeed once. An unchanged declined exact car is excluded under `untilRelevantConfirmedBriefChange`. Semantic confirmed preference/essential content is compared with the decision's saved brief, ignoring provenance-only changes, pause/resume and equipment array order. A relevant confirmed change permits re-evaluation through the same gates. Expiry and missed mail never enter dislike or priority calculations.

## Claim handoff and replay

`claim.tryClaim(employeeContext, claimInput)` is mandatory. `claimInput` contains `{ runId, eventId, operationId, employeeId, entitlementSlotId, renewalId, orderUuid, quote, expectedVersions, reasons, renewalDue, score, lottery }`. The quote pins exact snapshot, employee facts, terms, evaluated versions, reasons and trade-offs. Expected versions include stock, slot, employee, brief, consent, policy and clock. The port must revalidate current permission, eligibility, essentials, versions and quote validity and atomically create its hold/offer/outbox through the existing shared claim authority. Allocation creates none of these records.

`ok` means the claim is secured; `conflict` or `stale-version` lets allocation consider the employee's next appropriate contender. Any uncertain/unavailable response leaves the run pending, without proceeding to another claim. The stable operation ID binds run/event/employee/exact car. An injected producer **must** replay that ID idempotently, including a crash after its commit and before allocation acknowledgement. It must preserve uncertain claims until reconciliation. Repeated calls with that ID receive the same quote.

The existing `event_receipts` row under `buddy-allocation` stores the trigger digest, source versions, immutable evaluated plan and progress before handoff. A pre-plan source read has its own attempt identity: if evaluation rejects that snapshot, an identical event retry can read repaired source records. The accepted prepare receipt freezes the plan. Each attempt advances by optimistic CAS. Completion records `{ state: 'allocated' | 'no-assignment', runId, event, evaluatedAt, policyVersion, assumptions, inputVersions, assignments, attempts, evaluations }`. `assignments` retain employee/exact-car/quote and grounded reasons. Reopening/replaying a completed event returns its original outcome without calling the producer. A pending replay resumes its saved plan; the claim port checks whether any current versions have changed.

Storage at scale (FUCQ-205, FUCQ-209, FUCQ-217, 8 November 2026): the pending plan is written once and holds the contenders plus the frozen pool of exact cars it evaluated. Each employee's evaluation is its own `buddy-allocation-evaluation` row; identical decision bodies are stored once as `variants`, with `cars` mapping each exact car to one, and `readAllocationEvaluation` returns full decisions. No quote is stored per eligible pair. The row keeps the employee's frozen evaluation inputs, and a quote is rebuilt only for a contender that is actually attempted, by evaluating that one frozen car (decisions are per car, so the quote is the one the full evaluation produced). The `buddy-allocation-cursor` row stays `{ next, count }`; each attempt is its own `buddy-allocation-attempt` row, written in the same transaction as the cursor step. Snapshot, step and completion transactions return a small marker, because every transaction result is also kept as a command receipt. Pending plans and cursors written before these changes keep their inline quotes and progress. The completed outcome and its returned shape are unchanged.

## Trusted cohort identity

`DemoIdentityAdapter.resolveEmployeeContext(controller, employeeId)` is an in-process presenter-only seam. It validates the current adapter-owned controller, canonical configured employee and matching seeded scheme/grade/slot ownership, then issues a frozen adapter-owned employee context. It preserves the controller's expiry and run guard and issues no cookie/session. Derived contexts cannot become presenters, resolve another employee, bypass resource checks or cross a reset. This method has no HTTP endpoint.
