## Versioned consumer contract

- `readTerms(context)` returns the version, digest, applicable declaration definitions, configured stages, validity and provenance.
- `submit(context,{commandId,source,expectedQuoteId,expectedStockVersion,termsDigest,declarations})` accepts only these fields. Source is `{type:cart|buddy-offer,holdId,expectedHoldVersion,expectedDraftVersion}`. Declarations contain exactly the applicable IDs with boolean true. Principal, run and entitlement are server authority.
- `readOrder(context)` returns the same durable snapshot and current pending/acknowledged/failure state without effects. A retrying identical submit drives reconciliation using the existing operation key. A changed intent conflicts. Order reads never recalculate historical terms or silently change driver/contact/old-contract/quote/stock snapshots.

Both source kinds use a converter with `prepare(context,source)` and `convertSelection(context,allocationInput,{commitSelection})`. Prepare returns verified draft/choices, employee, driver/licence, old contract and source versions. The source authority repeats its live validation, opens its repository transaction, calls the trusted `commitSelection(tx)` while the source hold is still active, then performs its existing conditional allocation in the same transaction. The callback writes the exact selection snapshot, pending operation and history; any typed error rolls all source and selection changes back. No external I/O belongs in this transaction. The converter returns its ordinary complete `ok` or `pending` envelope; ordering rereads its own operation and checks source authority. This function is injected at trusted startup, never accepted as HTTP input. A missing buddy converter is unsupported, not an inferred manual claim. FUCQ-108 supplies the actual buddy converter and offer decision integration; this checkpoint adds no offers, email or events for that journey.

For retained source implementations, `allocate(context,allocationInput)` remains a compatibility checkpoint path using two transactions. It does not satisfy final atomicity acceptance. New composed producers must supply the transactional method. `createManualOrderConversion` exposes the new method only when the actual claims service has it, forwarding the same callback without implementing claims rules. Gary's held FUCQ-66 producer currently has no `convertSelection`; it remains unchanged and its existing allocation path is labelled separately in evidence.

`createManualOrderConversion({claims,manual})` consumes the inspected FUCQ-66 `readClaim`/`allocate` and its `ManualContextService.revalidateHeldSelection` port. It rejects incomplete/refreshed drafts, changed context, non-eligible driver/licence/stock decisions and missing order-review before persistence. FUCQ-66 repeats current account/driver/licence, entitlement, draft, stock/policy and quote checks during allocation. The current integrated base lacks this held-selection revalidation port; the service fails unavailable there until F66 integration. ## Durable state and external-shaped protocol

The stable operation/idempotency key hashes run, employee and entitlement. One pending-operation primary key prevents two selection intents for the same entitlement. In the source transaction callback, submit checks exact hold ownership/state/expiry, quote/draft/policy/validity, stock revision/facts/configuration/seven-digit number, employee authority, slot and run clock/policy. It persists `selection-received` with an immutable snapshot and `pending_operations` type `selection-order` / state `pending` / phase `allocation-pending` before an external-shaped ordering call. The payload records `atomicConversion:true` for the new path, so retries and ticks observe its source's reconciliation and never initiate a second allocation.

F66's allocate remains the sole claims authority. The common service does not infer allocation from a pending return. It verifies the existing hold, paired claim, exact stock and entitlement all say allocated before changing to `handoff-pending` or calling ordering. The order identity is always the stock's existing `orderUuid`, seven-digit `orderNumber` and `configurationId`. No new order number, VIN, approval, collection or current-car relationship is created.

A persisted context is an audit/scope snapshot, never a fresh employee credential. Only authenticated submit can initiate conversion. Ticks observe the source authority's own reconciliation and drive ordering after confirmed allocation. Atomic conversion cannot leave selection intent committed before conversion starts. In the retained two-transaction compatibility path, such a crash still requires an authenticated retry.

The source hold reference is inside the operation payload, deliberately absent from top-level `holdId`. F66's snapshot currently interprets any pending operation linked by top-level holdId as a pending claims operation. Linking the ordering intent there would prevent the converter from allocating. This compatibility convention is exercised against the actual held F66 implementation.

Every ordering attempt calls `reconcile(operation)` before resend. Only authoritative `not-found` matching operation/run/exact order may call `execute(operation)` with that same persisted idempotency key. Confirmation must match all scope fields, existing configuration and order number, and the first configured approval stage. Malformed/wrong-scope responses and exceptions stay unknown/pending; scoped rejected/unsupported responses persist failure. Confirmed allocation remains occupied throughout unknown outcomes and failure. A local receipt never invents BMW success.

The synthetic adapter is explicitly fictional. Its simulated provider receipt is stored idempotently in the same repository, rather than an in-process map; reopen and response loss preserve the provider result. Its boundary status is **double-only**: BMW's target ordering platform and API adoption/shape remain unverified, and no real system was called. The malformed-provider test supplies a deliberately divergent acknowledgement and proves rejection. Remote adapters owe scoped conditional authority/idempotency and the same execute/reconcile error semantics; no network retry timer or credential access is supplied.

History lives under `ordering:history:<employeeId>` with `selection-received`, then `selection-acknowledged` or `selection-handoff-failed`; projections read the same operation store. Account HTTP history wiring remains outstanding. Internal operation phases are not employee approval stages. Failed allocations remain conservatively attached to this entitlement; no automatic fresh selection/reallocation is enabled by this checkpoint.

## FUCQ-108 buddy handoff

An accepted buddy offer uses this same service and adapter; there is no second ordering adapter. `OfferDecisionService.decide` (accept) now takes `termsDigest` and `declarations`, builds a server-owned employee context from the stored offer and calls `ManualOrderService.submitSource(context, input, { converter })`. `submitSource` is trusted in-process composition only (never routed to HTTP; the runtime's employee `converters` map stays cart-only) and accepts only `source.type: 'buddy-offer'` with an atomic converter. It shares one private path with `submit`: same input checks, terms digest, declarations and `commitSelection`.

The converter's `prepare` (`server/gcsp/offers/buddy-conversion.js`) reads the stored employee record: valid contact, an eligible employee driver with a valid car licence, and for a replacement the return car model, contract end and a non-negative odometer, else conflict `contact-required`, `driver-review-required` or `return-data-required`. Its `convertSelection` runs the offer-decision transaction, which calls `commitSelection(tx)` after the allowance and revalidation checks and before the offer, hold, claim, stock and slot move to accepted/allocated. A refusal rolls the whole transaction back. Buddy quotes carry `briefVersion`, so `source.expectedDraftVersion` is compared with it. The allowance is rechecked through `PolicyService.getAllowance` against the pinned quote's points (`allowance-exceeded`); the quote is never requoted.

`readOrder` and the accept response carry `progress`: `{ schemaVersion, selectionState: handoff-pending|acknowledged|handoff-failed, approved: false, current, stages: [{ name, state }] }`, with `selection received` first, then the pinned `ordering.approvalStages.v1` names (HR approval only when configured). The first approval stage is `waiting` once acknowledged. `approved` is always false here; approval progress belongs to the lifecycle service. The brief records the selection as a `brief-selection:v1` receipt (`selection-recorded`, keyed by employee and entitlement, with offer, hold, order and operation ids) in the same transaction, since briefs are immutable. An uncertain adapter outcome stays pending and is reconciled by the `selection-order-reconciliation` tick before any retry.
