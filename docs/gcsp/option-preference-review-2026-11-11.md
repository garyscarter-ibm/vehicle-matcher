## Draft interpretation

- **Well-specified:** `1` gives a normal distinct desirable, usable capability one point; higher numeric values give it more weight (`2` highly desirable, `3` exceptional/unicorn); `0` excludes it; `Bundle` requires resolving contents; `Unknown` waits for a description. Never add a bundle and the same included components. Use the highest applicable reviewed weight for a capability once. Heating and ventilation are separate functions; two heating tier codes are one function. Overlap groups are prompts for reconciliation, not a complete package bill of materials.
- **Other evidence:** `0` means no justified inference; `+1` supporting and `+2` strong evidence toward the high slider endpoint. Negative evidence points toward the low endpoint. Sportiness runs relaxed→sporty; comfort runs simple/functional→comfortable/luxurious; economy runs driving-first→economy-first; size runs compact→spacious. Body/fuel use explicit category evidence or `None` in the workbook; all draft rows use `None` because model facts are authoritative.
- **Avoid invented benefits:** colour-only choices, administration, service plans, regulatory/baseline equipment and inactive preparation codes get no richer-spec credit. Premium materials and sporty styling have explicit subjective proposals for review. Wheel size alone never proves handling or poor ride. Aero-wheel and mild-hybrid economy evidence is weak, without a quantified saving. Sliding rear seats have weak proposed legroom evidence; towing/storage/folding seats do not imply a larger cabin.
- **Use existing importance:** option evidence belongs inside the relevant selected preference and its chosen importance. Use the strongest signal once per underlying capability, keep each dimension bounded, and avoid duplicate model/tag evidence. M Sport packages and their component markers share `sport-package`: their sportiness evidence must never stack. The hidden preference adds no visible control or user-input completion credit. A monotonic bounded weighted-total-to-score calibration remains to be built after review; more distinct desirable capabilities or a higher reviewed weight must never reduce this score.
- **Keep prior rules:** essentials, points limits and the approved FUCQ-381 points-usage ranking remain in place. This proposal changes preference evidence; it does not bypass eligibility or replace the points-use tune.

## Source and implementation boundary

Observed BMW option descriptions come from retained source observations (`report.candidates[].definitions[].longDescription`). Their original source envelopes have `admission:false`; they are suitable provenance for this review and have not been admitted as a universal production dictionary. **46 codes have multiple labels** (519 distinct code/description pairs), including cockpit/HUD and Technology/Technology Plus. The main description is a lead source label; resolve the variants by model/trim before using it for scoring or display. Preserve source-reported option types separately from the proposed normalized review categories. All 53 archive-only source paths have a Git blob and archive source-commit pointer in the companion JSON.

An option’s availability in a dictionary does not establish selection or fitment. The registered catalogue retains selected configurations, while VIN-verified fitted evidence remains a separate authority. Only actually selected/fitted, active usable capabilities may affect a vehicle’s score. Subscription/preparation codes need entitlement checks. Current loss of exact readable configuration details upstream is already captured by **FUCQ-382**; this deliverable does not claim that gap is fixed.

Current scoring uses six visible preferences and model/tag evidence, with no general richer-equipment preference. This task adds review artefacts only: no runtime scorer, source-admission, UI, policy version, Jira or deployment changes. The next implementation should follow the reviewed matrix and validate richer-versus-basic comparisons, preference tradeoffs, bundle deduplication, inactive/unknown options and the existing points-usage boundary.
