# Existing adapter readiness — 13 November 2026

Gary asked how close the application already is to proposed Epic 3, because replaceable adapters were an original requirement. Source baseline: `84742c4ce`, current checkout `gcsp-poc-dev`. This is a bounded code/contract assessment and focused validation, not a live-integration or exhaustive path audit. No runtime code, data, provider configuration or Jira issue changed.

## Finding

**The adapter architecture is substantially present, with executable substitution evidence.** The [original brief](demo-brief.md#binding-boundaries) already requires replaceable external-data/system adapters and the same application logic for fixture-backed and real-backed inputs. Epic 3 should complete and prove that existing architecture, rather than imply a new adapter layer must be built from scratch.

The stronger claim that every operational provider can now be exchanged with no application-service change is not yet established. There are concrete remaining protocol and composition gaps. No defensible percentage follows from this small assessment; interface existence, substitution tests, complete runtime wiring and verified live services are different evidence levels.

## Specific remaining work

1. **Finish remote offer decisions.** [OfferDecisionService](../../server/gcsp/offers/decision.js), around lines 167 and 291, refuses remote-mode accept/decline with `remote-decision-protocol-required`. A remote Buddy claim can be confirmed, but its offer cannot complete through the current local decision path. This is an actual application-protocol gap, not just a missing live-service adapter. Preserve pending custody, release confirmation and order conversion when completing it; removing the guard alone is insufficient. [The existing remote-decision plan](evidence/fucq106/remote-decisions-plan.md) already records this work. The [FUCQ-106 delivery result](../../_dev/done/2026-11/DEV-2026-11-04-074.md) treats remote adapter/handoff consumption as outside that delivered Story's scope; this assessment does not reopen or rewrite its acceptance.
2. **Make the complete provider set selectable and isolate demo preparation.** Runtime already injects some dependencies, while assembling manual-context ports and several synthetic ordering/lifecycle providers itself. It always opens a synthetic environment, seeds demo principals and adopts demo profiles/model facts. A live configuration needs explicit provider composition and separation from that preparation. This is remaining runtime work, rather than a reason to replace the service architecture.
3. **Review remaining synthetic assumptions at the boundary.** For example, lifecycle services import operation identifiers from synthetic-provider modules, and document acknowledgement explicitly accepts `"synthetic"`. Some are harmless placement/provenance choices; others represent capabilities a live service must actually support. Review them against each required contract before claiming complete interchangeability. This assessment does not infer a production defect merely from a synthetic marker.
4. **Complete the inventory and connected proof.** Credit the tests already present, then map the remaining reads, commands and events to their authoritative ports. Demonstrate provider substitution through actual runtime composition for an employee-context/stock-to-recommendation flow and a claim/offer-decision/order/status flow. Preserve explicit capability gaps; fixtures cannot verify an unavailable upstream service.

Actual BMW identity, HR, stock, ordering and lifecycle integrations still need their own authorized service access and contract evidence. That is separate from proving the internal replacement boundary.

## Epic refinement

Recommended title: **Complete and prove GCSP's replaceable service adapters**. Its starting point is implemented ports and working provider protocols, with the residual scope above. Existing tests and capabilities count as evidence rather than being commissioned again. Reconcile remaining work with the original capability/Story records before authoring new Stories; retain previously agreed exclusions and acceptance decisions.

The Java/Quarkus port should carry forward these contracts and decision fixtures. Where practical, complete remaining provider-composition and protocol work in those Java slices, preserving any working Node journeys until cutover. A wholesale JavaScript adapter refactor before that port is not established as necessary by this assessment.
