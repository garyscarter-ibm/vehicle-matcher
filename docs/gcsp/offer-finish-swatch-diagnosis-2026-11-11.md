# Offer colour circles diagnosis — 11 November 2026

Gary asked to investigate why the colour circles still do not work while the Your cars / Your offer styling pass was in progress. This is a separate existing cosmetic defect, Low severity: the accurate readable finish names remain present and no decisions or vehicle identity are affected. Jira writes are paused; retain this report for later linked Bug reconciliation. No swatch repair is claimed or included in the typography change.

Origin relationship: FUCQ-383 introduced finish swatches in the full-width vehicle offer; confirmed by `docs/gcsp/vehicle-offer-stories-2026-11-11.md`, component history (`dc446235`, later compact revision `22176eb2`) and the FUCQ-383 regression in `gcsp-offer-view-render.test.js`.

Reproduction: open `/blocks/gcsp/offer/preview.html?fixture=fuller-offer` at desktop width. Alpine White and Black Veganza have hatched neutral circles instead of white/black accents. Expected: known finishes have useful colour accents beside their labels; genuinely unknown finishes remain neutral. The supplied screenshot/rendered review is in the styling evidence directory.

Diagnosis (verified): `finishLabel` in `blocks/gcsp/kit/vehicle-decision.js` paints only a supported `shade` key through the shared `SWATCH_HEX` palette. Without it, it applies `is-unknown` and the neutral hatched style. `offer-view.js` passes `fact.shade`, but `offer-projection.js:detailFact` emits labels/values/units/items/provenance and never emits shade; `fullerOffer` fixtures also emit finish names without shade. The data producer explicitly records exact source swatches as `unknown/source-swatch-unavailable` in `configuration-definitions.js` and `vehicle-details-contract.js`. The existing regression deliberately expects neutral swatches for Alpine White / Black upholstery when only prose is supplied. Therefore this is missing colour-family integration, not CSS hiding a supplied colour. No stale cache or browser issue was found.

New upstream evidence: current gcsp-poc contains `stock.paintColourFamilies.v1` and `docs/gcsp/paint-colour-family-mapping-2026-11-11.md`. The policy table is deliberately not activated in an offer resolver; exact source swatches and a broad decorative family are different facts. Generic P0490 must stay unknown without an actually selected specific Individual shade. Upholstery needs its own supported mapping; the exterior table cannot establish it.

Next repair slice: connect the actual selected paint code through the existing policy table to a clearly separate decorative shade/family, preserve its provenance through quote/presentation, and resolve upholstery from supported selected upholstery data. Preserve readable labels and neutral fallback for absent/conflicting/unsupported inputs. Update the fuller-offer fixture to use the same contract and add producer-to-renderer regression coverage for white, black, named paint families, generic Individual and missing/mixed upholstery. Do not guess an exact paint sample or parse arbitrary prose to bypass missing source data. This investigation changes no backend contracts, mappings or swatch behavior.

Subsequent authorised remedy: Gary chose “Build shared demo mapping”. The shared finish component now resolves exact recognised display names through a generated decorative catalogue sourced from canonical policy; Alpine White / Black Veganza display white / black without fixture-only shade fields. Unknown, generic and ambiguous finishes retain neutral hatching. See `demo-finish-shades-2026-11-11.md` for implementation, 245 passing selected checks, desktop captures and the known unrelated ratchet omission. This resolves the demo's missing accents for recognised names. The more extensive selected-code/provenance plumbing described above and exact manufacturer samples remain outside this cosmetic scope; no exact source-swatch availability or wider Story acceptance is claimed.
