# Offline fleet qualification

`fleet-plan.v1` is an executable qualification contract. It contains no collector and makes no outbound calls. From the repository root:

```sh
node scripts/gcsp/fleet-plan.mjs --config server/data/gcsp/vehicle-evidence/fleet-plan.json --offline
```

The report goes to stdout. Exit 0 means the offline contract passed; exit 1 means qualification failed; exit 2 means invalid arguments or unreadable/invalid JSON. Every argument combination other than `--config PATH --offline`, including `--real`, refuses before reading configuration. Neither mode writes artifacts, accesses a database, allocates a VIN or changes policy.

The shipped plan deliberately exits 1. It proves three distinct GB i5 eDrive40 M Sport Touring configurations: model `T5MJ`, AG `72HH`, configurator range `G61E`, chassis/generation `G61`, GB/RHD/en-GB, catalogue and order date 1 November 2026, effect date 5 January 2027. Complete solver selections are retained in the FUCQ-4 pilot, with 48/48/49 elements respectively. Each contains the `SE000001` accessory, so these numbers are not factory-option counts or verified fitted equipment. The three complete lists are validated against that local evidence. Rim-family classification, model year, plant, production era/date and compatible GB profile remain unknown. Effect date is not evidence of actual manufacture.

The active demonstration target is at least 200 real constructible configurations covering every selected scheme model line. The three proved configurations leave a count shortfall of 197; the scheme-to-current-catalogue mapping is unselected. The legacy 10,000 target leaves 9,997; actual collection under FUCQ-61 is deferred until after 12 November 2026. A claim of 10,000, more dates, alternate metadata, VINs or duplicate solver results cannot supply distinct coverage.

## Evidence and identity boundaries

Corpus identity is standard padded Base64 of `vgModelCode:sorted,complete,resolved,base-option-codes`, excluding every selected accessory. The plan uses configurator model code `T5MJ` as the current HLD's VG-code base; the BMW VSS implementation instead uses AG `72HH` without Base64, and that target-model-base uncertainty remains documented in the HLD. Full `completeSelectedElements`, including accessories, remain independently validated source proof. The report rejects duplicate builds across families and date/source aliases. It retains the configurator range separately. Exact stock cars have mutable per-run Postgres order references/orderUuid outside this artifact. VINs belong only to delivered/current employee cars; this tool neither generates nor retains them. AG, chassis and whole VIN descriptor are separate fields.

The trusted offline loader reads the existing FUCQ-52 registry, the dated BMW GB catalogue snapshot and the three retained pilot solver records. It requires exact model/AG/range/generation/market/steering/locale/order/effect/catalogue context and full resolved elements, constructibility and preserved requested model/options. Profile resolution uses the existing in-process registry's current-car structural selection contract solely to check compatibility; it does not allocate a corpus VIN. Year, plant, era, derivative and other profile identity fields must match exactly. Profile source, version, observation date and confidence must match. No nearest model or substituted identity is accepted.

The five enabled WBA/WBS/WBY/5UX/5YM profiles are US/LHD structural references, with some technical fields explicitly unknown. They do not bind the GB/RHD pilot. UK candidates remain unactivated, and this story does not close missing external corroboration. Multiple distinct complete builds are required for every requested WMI. Additional 3MW/3MF/WB5/WBX filing references are recorded without activation. The October 2024 scheme matrix is an eligibility source, never a current catalogue or VIN profile.

The exported qualifier accepts injected evidence for isolated tests. Tests use 200 explicitly synthetic builds over five structural reference contexts, with synthetic catalogue and permission records. Their report says `contractOnly: true`, `sourceKind: synthetic`, `contractQualified: true`, `qualified: false` and `synthetic-contract-only`. These test records are not shipped collection evidence and never increase `distinctProved`. Test-only CLI injection can exit 0 for this contract demonstration. A future operationally qualified report requires real observed evidence, all selected coverage, and explicit permissions. Synthetic tool, permission, catalogue or profile provenance prevents operational qualification even when every build is labelled observed. Source/unknown/profile-failure presentation fields remain visible; no screen or screenshot is added.

## Before a collection implementation is authorised

Select and record source access, data retention and image display permissions independently, with source, date, confidence and permission basis. Public technical access is not reuse permission. Choose exact catalogue contexts, complete resolved selections and corroborated enabled profiles. Supply every scheme model line and its eligibility provenance. Extend the trusted offline evidence loader when independently qualified evidence becomes available; a plan's self-asserted booleans cannot qualify a build.

Select all numeric work inputs: candidate requests, solver candidates, OTD configurations, image configurations, views per configuration and maximum image bytes per view. Solver and OTD counts must cover all represented builds. Each image configuration includes one manifest request plus the selected image downloads. No Cartesian combination is assumed constructible.

Choose hard maximum requests, image requests, cache entries/bytes, concurrency, per-attempt timeout and total duration. Retry count is finite (0–20), with explicit initial/capped backoff, multiplier (1–10) and allowed retry statuses. Permission/authentication failures are not retryable. Stop on budget exhaustion, permission revocation, substituted identity, profile mismatch, source failure, retention violation or full destination. These values remain null in the shipped plan because no run budget has been selected.

The deterministic projection charges every cache miss its first attempt and all retries. It reports candidate/solver/OTD/image subtotals separately. `cold` requires zero hits. `verified-hits` requires exact-key prior evidence and hit counts no greater than the declared work. Trusted cache-entry corroboration is not implemented in this version: any positive declared hit refuses with `unproved-cache-hits` and still projects every request as a miss. A self-asserted hit count cannot reduce a budget. The report separates declared hits from effective zero hits. Keys include full context, complete selections and provider version; changing a date invalidates reuse even though it does not create a distinct configuration. TTL and maximum bytes per entry are explicit. Cache capacity conservatively covers all logical entries, including hits. The elapsed upper bound sums all attempts at their full timeout plus capped backoff for every miss; it is serial and remains conservative at any declared concurrency. Overflow or any exceeded hard limit refuses. Missing inputs produce `projection.status: unavailable`, never invented numeric estimates.

Choose evidence and image destinations independently: absolute normalised paths, expected bytes, non-public storage and `reusable-non-personal` retention. Image capacity must cover the declared maximum image bytes. Evidence capacity must cover projected `cacheBytes`, a conservative allocation for all logical reusable data/cache records, including existing entries and candidate/solver/OTD/image metadata; `entryBytes` must be selected as an upper bound for those records. Any destination expected to reach 256 MiB must be directly under `/Users/usget/Library/CloudStorage/OneDrive-IBM/Claude/`, without an intermediate local copy. Placement does not prove cloud upload. The offline command checks the declared contract without creating or probing destinations; an eventual collector must check actual capacity before writing and stop at its limits.

Retained categories are allowlisted: shared type codes, resolved selections, sanitised evidence/provenance, technical facts and permitted representative images. Discard sampled real VINs, plates, serials, private identifiers, private vehicle URLs and captures. The validator rejects unknown fields and structured extension payloads at every retained schema location, and scans declared metadata for identifier fields, complete VIN/UK-plate shapes and identifier-bearing URLs (including customerId/userId query parameters). Privacy or unknown-payload rejection returns before projecting any supplied metadata, with bounded generic error codes. These shape checks do not establish that arbitrary prose is non-personal; retained source metadata still requires review. Do not add arbitrary provider payloads, screenshots, opaque URLs, garage/state identifiers or credentials. Review any future evidence source before adding it to the trusted loader.

Open decisions remain compatible GB profile corroboration (including year/plant/era), full current model-line catalogue mapping and capacity, source/access/retention/display basis, numeric work/cache/retry budgets and destination selection. These are real collection preconditions; they do not prevent the offline refusal contract from being reviewed and tested.

## Scoped verification

```sh
node --test server/test/gcsp-fleet-plan.test.js
```

Synthetic five-WMI success is separate from shipped refusal. Tests cover profile and context mismatch, semantic duplicates, unproved/substituted selections, missing provenance/permissions/budgets, retry/cache arithmetic, retention/destination rejection, presentation labels and subprocess CLI statuses. Network entry points are instrumented to throw and counted during both synthetic contract qualification and shipped refusal. No full suite or live source request is needed for this isolated CLI/data change.
