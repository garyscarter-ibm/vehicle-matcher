# Captured notification dispatch · FUCQ-93

`server/gcsp/notify/index.js` supplies `NotificationDispatcher` and the `MailTransport` port. Its default `CapturedTransport` stores a fictional employee's rendered message in the existing run-scoped `notification_outbox.outcome.message`. It creates no external email, address, credential, sender, infrastructure or second store. There is no viewer or token minting here. FUCQ-100 owns the committed hold/offer/job producer and FUCQ-97 owns the later presenter viewer.

## Trusted composition and lifecycle

Construct a dispatcher with the existing `{ repository, policy, clock, environmentId }` ports and pass it to `buildServer({ gcspClock: clock, gcspIdentity: identity, gcspNotify: dispatcher })`. Register all other clock handlers before server creation. `dispatcher.start()` registers `captured-outbox` at the existing `outbox-dispatch` stage, subscribes to the repository's actual `afterCommit(observer)` port and drains committed work before the clock seals its registry in startup reconciliation. `start()` is idempotent per dispatcher. `close()` unsubscribes its commit observer; close the repository at backend shutdown. Supply a new runtime/dispatcher after process restart.

The repository invokes commit observers after its backend releases the transaction and only following a successful actual commit. Rollback, replay and uncertain/failed provider acknowledgement do not masquerade as a new commit. Observer rejection cannot change the original successful command result. Notification commands use the reserved backend `notify:` namespace and the observer ignores their bookkeeping, preventing recursive dispatch. Concurrent triggers are coalesced and request a follow-up drain so work committed during a drain is picked up. Independent dispatcher instances share the repository's CAS/command receipts and the captured transport's idempotent acknowledgement.

`MailTransport.send({ context, job, message, now })` returns a safe `ok` acknowledgement or a typed failure; implementations must use the same run/job identity idempotently. The dispatcher durably marks an acknowledged attempt sent, while the default captured transport commits the message and acknowledgement together before returning. Unknown provider acknowledgement details never enter job outcomes or logs. Injected acknowledgements in tests exercise this port boundary without implementing real delivery.

`dispatchPending(expectedContext?)` resolves the persisted current run for the trusted environment, uses the clock's current instant and run policy, and processes pending/due retrying/interrupted sending jobs. A supplied old run is refused. There is no HTTP dispatch route, unattended polling or browser-controlled principal. The service principal is backend-owned, as in clock startup. Recipient identity must match an employee in the canonical `identity.demo.principals` registry; no recipient email address is used.

## Producer and viewer contract

The producer commits the exclusive hold, offer and job together. A job has `jobId`, `offerId`, `recipientId` (employee ID), `messageKind: offer`, `messageVersion: '1'`, `state: pending`, `attempts: 0`, `idempotencyKey: offer:<offerId>:notification:offer:1`, canonical `inputDigest` and private `payload.offerLink`. Run ID is a separate key. This consumer reads the existing offer/quote/employee rows; it never creates a hold, offer, employee allocation or token. Link generation and authorization remain with the owning offer story.

| Job state | Persisted presentation fields | Meaning for the later viewer |
|---|---|---|
| `pending` | Stable job/offer/run, zero attempts | Committed and awaiting dispatch. |
| `sending` | `attempts`, `outcome.attemptedAt`, `policyVersion` | Durable attempt; restart retries its same job identity. |
| `sent` | `transport: captured`, `outcome.capturedAt`, `outcome.message`; null error/next time | Captured demonstration message; no external email was sent. |
| `retrying` | Attempt, fixed safe error, demo-clock `nextAttemptAt`, policy version | Temporary delivery failure; the account offer remains visible. |
| `failed` | Attempt, safe error, null next time | Retry budget exhausted or message facts invalid/inactive. No automatic requeue. |
| `stale` | `outcome.error: stale-run`, null next time | Prior-run unsent work retired atomically by reset; cannot send into the new run. |

`outcome.message` contains `{ runId, jobId, recipient: { employeeId, name, fictional: true }, subject, textBody, htmlBody, offerLink, capturedAt }`. `capturedAt`, attempted/retry instants derive from DemoClock. Storage creation/update timestamps remain repository metadata. Captured messages and token-bearing links are private backend state for an authorized future viewer, never public command outcomes, diagnostic logs or receipts copied into documentation. The transport and dispatcher return safe acknowledgements/counts, not message bodies. Sent history remains intact through reset; other old jobs become stale in the same retirement transaction.

Retry rules come only from `PolicyService.getAssumption('notify.delivery.v1', read)` pinned to the run policy. The canonical seed explicitly labels the revisable assumption: maximum three attempts, exponential 30-second initial delay capped at 300 seconds. No consumer/test fallback duplicates these defaults. Changing the canonical entry changes subsequent attempt scheduling and budget; historical attempts keep their policy version. This is demonstration behavior, not verified BMW mail policy.

Delivery exceptions and provider error text are discarded. Persisted/logged errors are fixed codes such as `transport-unavailable`, `message-invalid`, `message-facts-unavailable`, `fictional-recipient-required`, `recipient-mismatch`, `message-version-unsupported`, `offer-inactive` and `offer-expired`. Optional diagnostic output contains only event/state/attempt/error, without links, tokens, recipients or arbitrary IDs. Stock, hold, offer and employee priority state are never written by the dispatcher.

## Presenter route (FUCQ-97)

`createOutboxRoutes(outbox)` in `server/gcsp/notify/http.js` adds `GET /api/gcsp/presenter/outbox` (presenter role, `presenter-control` purpose). Compose it as `buildServer({ ..., gcspOutbox: { repository } })`; without it the route answers 503 `unavailable`. It reads the current run's `notification_outbox`, drops `stale` rows and returns a safe projection (`jobId, messageKind, state, attempts, error, nextAttemptAt, time, recipient, subject, textBody, htmlBody, offerLink`) newest first, never `payload`, `idempotencyKey` or `inputDigest`. Employees and Greg get 403 `forbidden`, a pre-reset cookie 409 `stale-run`, and any query parameter is `invalid`. See [presenter-outbox-contract.md](presenter-outbox-contract.md).

## Presentation and repeatable trials

This is a backend presentation contract, with no application screen or component change. The later viewer follows the [experience contract](experience-quality.md), supplied shell/sidebar/palette references and [shared kit](../../COMPONENTS.md). The email uses semantic headings, a labelled text link, a visible copyable URL, an expired-state explanation and a plain-text alternative. Missing vehicle facts say to check the account instead of inventing details. It escapes dynamic HTML, rejects executable/network-path/credential-bearing URLs, removes em dashes from copy and contains no scripts, event handlers, remote assets or font requests. Arial with a generic sans-serif fallback is an intentional email-safe font choice, separate from application font styling.

Run `node --test server/test/gcsp-outbox.test.js` from the worktree root for repeatable synthetic seed/commit/dispatch/retry/reset trials. The fixtures use the real repository, DemoIdentityAdapter and DemoClock; their committed offer/job rows are test inputs rather than a new product producer. The checks cover startup capture, the registered tick, real post-commit dispatch, rollback, concurrent/idempotent/reopened capture, failures/backoff, terminal failure, unchanged account/stock state, interrupted attempts, reset while capture is in flight, old-run stale records, canonical fictional recipients, safe template/missing/expired states and actual emitted token-free diagnostics. Retry trials advance DemoClock to the stored next retry instant; they never wait for wall time.
