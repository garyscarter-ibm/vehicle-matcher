## The claim we should be able to demonstrate

> The Angular 21 frontend obtains application data and performs business actions through our Java 21 / Quarkus backend API. Every external system dependency sits behind a dedicated backend adapter contract. Our demonstration uses synthetic or recorded providers where live services are unavailable. A conforming live adapter can replace a provider without changing the frontend or core application logic, provided the live service supplies the required data and capabilities.

This is the target completion claim to prove, not a statement that the current application already satisfies it. The Java port changes the backend implementation once; later provider substitutions should preserve that implementation's application logic.

There are two different boundaries: **Angular API clients** connect the browser to our backend; **backend service adapters** connect application services to external systems. The frontend never selects a real or mock upstream provider. External authentication redirects and approved image/static-asset delivery may use their own hosts; application data and business commands still follow the backend boundary.

“All data is mocked” would misdescribe the current foundations. There is a PostgreSQL repository, a Brevo mail transport implementation, source-backed vehicle snapshots and synthetic operational providers. This proposal does not claim that any particular live transport is currently enabled or that BMW services are integrated.

Application-owned state, employee-entered preferences and calculated recommendations also need a clear home: the backend repository and application services. They do not require invented external services or one adapter per field. Adapter boundaries follow coherent upstream capabilities; one real service can implement several ports, and one capability can need several sources.

## E1 — Run GCSP through an independently hosted frontend and backend API

**Intent:** As the team maintaining GCSP, we can release a static frontend independently of the backend while users retain the agreed authenticated journeys and the new app preserves its state between ordinary restarts. Initial cutover may reset the agreed legacy operational state.

### decided / proposed scope

- Publish the complete GCSP frontend as static HTML, JavaScript, CSS and assets. Move request-time asset preparation into the frontend build. The backend supplies APIs and application services rather than employee/presenter HTML pages.
- Give every frontend consumer one consistent API configuration and request boundary. Reuse the compiled Angular bundles across environments, supplying public API/OIDC settings at deployment without recompiling Angular. Keep provider/client secrets and private service configuration on the backend. Public frontend configuration may identify the application API, OIDC issuer/public client/scopes and presentation settings; Angular holds only the user credentials/tokens required by the agreed public-client flow, never a client secret.
- Replace HTML-request session redirects and presenter-cookie setup with Angular OIDC sign-in, bearer-authenticated API context and dedicated presenter-role operations. Enforce authorization, eligibility, ownership and business transitions on the backend; remove presenter principal impersonation.
- Define replacement deep links, refresh, role navigation and brand/context handling. Newly issued offer links require sign-in/return and ownership checks; legacy GCSP URLs/API consumers need no backward compatibility. Update shared launcher/handoff links while preserving Used Cars. Define asset caching for independent releases.
- Retain Render and PostgreSQL. Define separate static/API services in the same repository's Render blueprint, using existing Render hostnames where feasible, with bearer requests, exact-origin CORS and the test-provider redirect arrangement proved on HTTPS. A purchased domain is a fallback only if needed. Gary creates the dev-branch Render environment with its own PostgreSQL database; prove reset/connection isolation from the running environment.
- Record frontend/API compatibility, independent release order and Gary's merge-triggered final switch so a frontend rollout does not depend on bundling its pages into the API deployment. Final interruption is acceptable and the old deployment need not be retained.

### acceptance

1. The frontend build can be served by a static host without a Node frontend process or per-user HTML generation. Static assets contain no private employee or presenter state.
2. Supported application reads and commands use the backend API. No frontend code accesses PostgreSQL, upstream operational services or server secrets directly. Backend authorization still refuses an unauthorized request made outside the UI.
3. OIDC login, logout/expiry, bearer-authenticated context, employee/Greg/presenter separation and newly issued offer-link ownership work under the chosen deployed origins, including direct entry and refresh. Renew where supported; otherwise sign in again and return to the authorized page with saved progress. Unfinished orders require confirmation without automatic submission after recovery. Sign-out clears app authentication and ends the provider session where supported; the next login can choose another account. Presenter controls grant no employee/Greg impersonation.
4. The agreed route inventory resolves to the correct frontend state. Invalid routes, unavailable APIs and expired sessions have usable recovery states; API errors never turn into an HTML fallback response.
5. Frontend and API artifacts can be built and released separately. Different public API/OIDC configuration works with unchanged compiled Angular bundle hashes. Demonstrate compatible releases with retained source/reference inputs and rehearse the agreed fresh-state cutover. New-app saved state and newly issued links survive ordinary compatible releases/restarts; the one-time legacy operational reset is explicit. Hand over Gary's merge into `gcsp-poc` and resulting Render replacement build; no old-deployment retention or rollback demonstration is required.

### validate

Use the existing route inventory and manual acceptance scenarios. Exercise the selected HTTPS topology in supported browsers, including Safari and private browsing, rather than relying on loopback or CORS inspection alone. Cover login/context, dedicated presenter controls/reset, saved preferences, manual claims, signed-in offer entry/decisions and Greg's operations; retain server authorization checks. Record actual results, failures and unrun cases. E2 supplies Angular-specific routing acceptance when its screens replace the current frontend.

**Boundary:** backend language conversion and adapter completion belong to E3. E1 introduces no microservices, repository split, database migration or Cloudflare move. It preserves existing behaviour and does not absorb performance tuning or new product features.

5. The Java runtime meets the adapter-completion acceptance below, including complete provider composition, separation of demo preparation and a connected substitution demonstration. Mock-backed journeys function through Java application services; API-compatible Node forwarding is identified as a temporary migration state.
6. Existing scenario/comparison sizes and a few simultaneous demo users demonstrate usable journeys/jobs within the selected Render resources. Record actual workload/resource results. Demonstrate release/readiness, rehearse the agreed fresh-state cutover and hand over retirement of the in-scope Node runtime through Gary's merge-triggered replacement.
