## 4. The authorised operational reset and the verification steps

**What resets.** At the switch the Java API starts on a new, empty database. Legacy Node state (employee and scenario
state, sessions, active offers and orders, old emailed links, operational learning and comparison history in `gcsp-db`)
is not migrated, drained or copied. Retained inputs (section 3) come from the image, not the database, so they survive.

**What never resets.** `gcsp-db` is never written or reset by this work. The Java database's identity row
(`GCSP_EXPECTED_DATABASE`, `GCSP_ENVIRONMENT_ID`, `reset_allowed` at first claim) refuses any reset aimed at another
environment's database. An ordinary restart never resets or reseeds.

**In-app reset (presenter).** `POST /presenter/scenarios/reset` or `/presenter/clock/reset` retires the run and
activates a new `demo-<hash>` run in one transaction; nothing is deleted and the command replays by `commandId`. It
needs `GCSP_SCENARIO_PROVIDER=demo` and a database claimed with `GCSP_RESET_ALLOWED=true`.

**Local rehearsal (slice 5, unrun).** One heavy run inside `_tools/test_stack.py heavy` with a `pg db create` database:
the Java jar and the Angular bundle at the branch head, the local OIDC issuer and headless Chrome, reusing
`scripts/gcsp/fucq438-release-proof.mjs` with one added phase rather than a new framework:

1. Fresh start on the empty database: readiness 200 with every required provider, `/context` 401 without a token.
2. Retained inputs served: policy version, comparison result digest `d388e337…`, model id `sha256:2ce1109d…` and
   corpus selection `28374a10…` read back through the API.
3. Create state: sign in as a test employee, save a preference, allocate an offer, note the outbox link.
4. Ordinary restart: the same state, run and link survive.
5. Presenter reset: a new run is active, the old run's link no longer resolves to an owned offer, the retained inputs
   in step 2 are unchanged, and a new allocation issues a new link that signs in and renders.
6. No Node GCSP process runs at any point (process scan), and the old database is never contacted.

**Hosted verification (Gary, after the dev environment exists).** Steps 1–7 of
`docs/gcsp/fucq438-release-handover-2026-11-18.md` section 3 stand, with two additions: in step 2, readiness must
report every `GCSP_REQUIRED_PROVIDERS` entry UP; after step 3, run one presenter reset and repeat step 3 on the new run.
