## Release port, count and reset gaps

FUCQ-92's actual constructor is `createStockReleaseService({ repository, policy, clock, identity, provider })`; `register()` installs handler `stock-release` at stage `release-pull`. Register before the first startup/tick seals the clock. Startup excludes release-pull. A normal presenter tick invokes it; the existing advance-and-tick endpoint needs no new release HTTP command. The source provider implements `pull({ runId, asOf, eventId, policyVersion, releaseSize, leadTimeDays, released, queuedSupply })`.

Minimum producer module closure is `stock/index.js`, `stock/port.js` and `stock/synthetic-provider.js`: the index statically re-exports the provider module. Its repository/PolicyService imports must resolve to the canonical runtime graph. `repository/index.js` and `policy/file-provider.js` match between the two checkpoints; repository/core differs in the FUCQ-100 notification-link receipt custody fix. Preserve canonical FUCQ-100 core. No replacement repository, seed or generic fixture overlay is required to compose the release service.

**Count diagnosis, source basis:** `controls.js` lines 134–136 selects the first release-pull outcome and reads `outcome.value.released`. The actual FUCQ-92 producer returns no such integer. Its successful release value is `{ kind: 'stock-released', runId, tickId, trancheId, ..., orderUuids, visibleOrderUuids, ... }`; `orderUuids` is exactly the cars newly inserted/promoted in the committed release. A successful empty pull returns `{ kind: 'no-release', runId, tickId, orderUuids: [] }`. Consequently this unadapted presenter would report no released count despite a genuine release. This is a static contract mismatch; no browser/runtime reproduction was attempted here.

Selected presenter adaptation, proposed for a later grant: consume the actual registered `stock-release`/`release-pull` result, require a successful known kind, matching current run/tick identity and a valid unique exact UUID array, then display `orderUuids.length`. Treat the genuine no-release empty array as zero. Preserve unavailable/pending/invalid/missing-handler distinctions; never infer count from a cue or `visibleOrderUuids` (the cumulative/tranche-visible list). Retain support for the existing explicit integer projection only if its identity/meaning remains defined. Do not add an independent stock counter or rewrite producer receipts solely to suit this UI.

FUCQ-92's optional `createStockReleaseHistoryPort(...).read(context)` is a different port. It requires a genuine employee context and projects cumulative employee-visible confirmed history. It is useful to the manual gallery but cannot substitute for a presenter's newly released count or establish current provider health. No presenter-authority bypass or new history route is proposed.

**Provider/reset diagnosis, source basis:** the current `createSyntheticStockProvider({ runId, version, label, windows })` captures one immutable run's plan. It returns stale-run for another run; the release validator accepts only shaped successful/unavailable pull outcomes and otherwise reports invalid. The clock's mechanics reset changes run and exact stock identities while retaining its services/registry. Merely registering a one-run provider once cannot establish successful post-reset release. Root/FUCQ-92/FUCQ-78 need a trusted source plan for each actual run, resolved by the tick's runId and actual generated identities/window data. Keep the release service/handler stable; do not replace a sealed clock or relabel old-run fixture stock.

The final source needs real FUCQ-77/FUCQ-78 constructible configurations and generated identity/visibility/facts/availability provenance. Existing TEST windows can demonstrate only an explicitly labelled isolated integration. They cannot establish business scenario preparation or real source delivery. If a provider car matches an existing unreleased identity, the release service preserves that row's facts/account/visibility; missing reset-seed source facts will not be repaired by supplying different facts on the pull. The actual importer/preparer must supply the required immutable facts before the release, or use a reviewed source path for genuinely absent cars.

The `next-release` command still advances to the configured **future named `release` cue**, then performs a normal tick. After that cue it explicitly becomes unavailable. FUCQ-92 can expose another eligible tranche on subsequent normal ticks; Step/forward To still invokes that handler. No next-window discovery/health API exists in the pinned provider. Keep that cue boundary explicit; do not present the current button as a dynamic next-window selector or invent a date from a local timer.
