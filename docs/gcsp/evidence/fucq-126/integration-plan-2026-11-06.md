## Available interfaces and actual composition boundaries

### Presenter, clock and reset

At the FUCQ-126 input, `createPresenterControlsService({ clock, identity, scenarios })` exposes `readState(context)` and `tick(context, input)`. `buildServer` registers `GET /api/gcsp/presenter/controls` and `POST /api/gcsp/presenter/controls/tick`. The command is exactly `{ commandId, expectedClockVersion, mode: 'step' | 'to' | 'next-release', to? }`; `to` is exclusive to mode `to`. Separate presenter-cookie authority, ordinary acting context, Origin/gate/no-store handling and stable original-body retry remain required.

`DemoClock.registerHandler({ handlerId, stage, handle })` accepts stable unique IDs before the first startup/tick seals the registry. Handlers receive the clock event, including current context/time/version and its transaction function. Configured stage order and then handler ID determine execution. Tick readback contains `handlerOrder`, matching `outcomes`, `missingStages` and completed/pending state. The presenter displays a count only from a successful `release-pull` outcome with an integer `value.released`; a future named `release` cue does not establish producer availability.

`createScenarioService({ repository, policy, clock, identity })` exposes `readState` and `reset`; registered catalogue/reset routes remain `/api/gcsp/presenter/scenarios` and `/api/gcsp/presenter/scenarios/reset`. Reset input carries `commandId`, `expectedRunId`, `expectedRunVersion`, `scenarioId`, `scenarioVersion`, `fixtureVersion`, `policyVersion`. Its private preparation delegates to the sole `clock.reset` transaction and existing session-renewal boundary.

**Exact policy-instance constraint:** `fixtures/scenarios/index.js` brands prepared objects in a private WeakMap with their `PolicyService` instance. `clock.reset` checks that instance against its own policy. FUCQ-103 constructs the clock with `readPolicy`, then returns a distinct `readPolicy.withPublicationPorts(...)` view. The returned view shares storage but not object identity. Root should construct `ScenarioService` inside that runtime with the original `readPolicy` and expose it as `gcspScenarios`. Simply constructing it outside with the returned publication view would fail the existing fixture trust check. This is a source-based integration constraint, not an executed defect reproduction; it requires no relaxation of the trust check.

All six business entries currently return their full required-capability list from `missingScenarioCapabilities`; only the separately labelled mechanics entry can prepare. Preparation returns configuration/selection metadata. `clock.reset` still calls `buildScenarioSeed`, whose rows are employees, entitlement slots and mechanics stock. It does not consume prepared briefs, offers or pending-operation rows. Therefore enabling business entries requires an agreed actual-service preparation/atomic reset boundary, not just a capability flag or component registration. A mechanism must also produce matching selected scenario/fixture configuration identities accepted by `clock.reset`.

Existing keys and tuning retain their values/provenance. File-backed policy is read-only; an all-present fresh command is rejected as a no-op. Keep the original accepted command for an unchanged replay.

The bundle's canonical definition digest is `a5a0476948ad990726829e343c40d7b5bc86d750177bb320d41751bcca4c9416`; its file SHA-256 is `0e09fc7cde7677724153265042eb1f7a122c88115762a736a4bdf02a4b2e470a`. `activateRunPolicy({ repository, policy }, context)` resolves policy at persisted `runs.clockInstant`, fences with run-version CAS, updates `runs.policyVersion` and `runs.versions.policy`, and rechecks the result. The delivered `createGcspRuntime` uses `MemoryPolicyProvider` in explicit memory mode and `PostgresPolicyProvider` by default, binds the publication view after identity/clock bootstrap, returns repository/policy/Greg/publish dependencies, and owns its provider teardown. It still does not return scenario, buddy, release, cases or notification dependencies. Existing manual/brief/activity/recommendation composition must be retained. FUCQ-103's stored-missing-step and default-memory runtime proofs are prior scoped evidence; this plan neither reruns them nor claims presenter/native activation acceptance.

`createGregPublishService({ repository, policy, clock, identity })` exposes read/preview/publish via `GET /api/gcsp/greg/policy` and the `/preview` and `/publish` POST routes. `createBuddyHoldService({ repository, policy, clock, identity, adapter })` supplies `allocate`, allocator-compatible `tryClaim`, `readOperation` and `start`. `adapter.mode` must be `local-synthetic` or `remote`; remote mode also requires `execute` and `reconcile`. `start()` registers `buddy-expiry` at stage `buddy-expiry`, and in remote mode `buddy-pending-operations` at `pending-reconciliation`. `readOperation(context, { operationId })` requires a genuine current employee context with matching employee/entitlement/run. The buddy source closure includes `offers/buddy-hold.js`, `buddy-remote.js`, `current-car-comparison.js`, `offer-token.js` and the stored-subject evaluator addition in `recommendation/index.js`. These support paths are pinned; importing only the constructor would not establish the delivered lifecycle.

Paused FUCQ-96 currently accepts only `ok`, `conflict`, `stale-version` from `tryClaim` and has no current-operation read.
