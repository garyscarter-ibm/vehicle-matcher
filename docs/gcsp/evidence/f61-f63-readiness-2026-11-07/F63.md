## Why the order-reference proof has a PostgreSQL boundary

[vehicle-lookup.js](../../../../server/gcsp/vehicle-evidence/vehicle-lookup.js) resolves configuration and VIN requests directly from the registry. A stock request additionally requires a trusted run/environment/principal context, `repository.currentRun`, and `repository.read` of the exact `(runId, orderUuid)` row. It verifies the exact order/configuration/synthetic association, then rechecks the current run to reject reset races. This existing port is the obligation to prove; another generic database smoke test cannot substitute for it.

[The HLD](../../../design/gcsp-high-level-design.md) and [repository contract](../../../../server/gcsp/repository/README.md) select PostgreSQL for durable mutable state. The explicit memory provider survives handle reopen only within its store and does not prove process-persistent SQL behavior. [createGcspRuntime](../../../../server/gcsp/runtime.js) defaults to PostgreSQL and refuses provider fallback. [publishStockOrders](../../../../server/gcsp/vehicle-evidence/vin-allocation.js) already writes immutable stock associations through the repository transaction.

The [order-reference preparation](../fucq63/order-reference-2026-11-07/README.md) passed three scoped cases/five memory-fixture stock rows across direct lookup, configured consumer and actual loopback HTTP. Its summary correctly says `fixture-proven-native-blocked`, `nativeProof:false`, `acceptance:false`: `GCSP_DATABASE_URL` was absent and no connection was attempted. Its earlier failed generator comparison remains recorded. Fixture mechanics do not prove real current-run stock production or persistence.

To claim the target stock integration, retain actual PostgreSQL evidence for an exact current run and a bounded list of real produced order UUIDs, using the existing allocator/publication and lookup/consumer/HTTP ports, with exact row/configuration/hash/snapshot/generator bindings and unchanged-run checks. Reuse suitable matching existing native evidence if it already covers that chain. A separately owned local cluster is one possible method; a provisioned approved PostgreSQL target is another. No new provider, schema, generic native framework, full scenario reset or local package installation is required by the original five AC. A passing 1–32-order sample proves its sample only; deployed persistence and full corpus recovery remain distinct claims.

Composition also needs an explicit record: [buildServer](../../../../server/index.js) supplies the local vehicle lookup's repository from `deps.gcspVehicleEvidence.repository`, or uses an explicitly injected lookup. The runtime's general `gcspRepository` dependency alone does not inject that stock lookup port. The prepared order runner supplies the real lookup/context deliberately.
