# F62 bounded static corpus loading plan — 7 November 2026

Goal: remove whole-corpus string, envelope and clone retention from the existing F54/F62 preparation, validation and runtime path while preserving immutable source authority, schema 1, the manifest, three JSONL filenames and synchronous lookup ports. Actual source counts remain independently evidenced; synthetic resource fixtures never establish source coverage.

The parent approved this implementation boundary after the measured small release exposed a 527,502-byte configuration file for 30 rows (17,583.4 bytes/row). The linear 10,000-row forecast is 175,834,000 configuration bytes, plus roughly 215 MB of retained admitted sources. Both exceed the current 64 MiB whole-file boundary. These are size forecasts, not runtime measurements or collected-source claims. The demonstration still requires 200 real constructible configurations across scheme model lines; the later 10,000 target and original claimed ACs remain unchanged.

The canonical HLD's pages 05/06 and `docs/design/gcsp-high-level-design.md` already place indexed versioned static artifacts inside the existing Node backend, separately from mutable employee/stock state. This repair adds no component, store, dependency or connection. The draw.io skill's step 0 therefore leaves the diagram unchanged. Runtime reads remain offline, and all packaged files remain inside Render's `server` root. No screen or component changes; experience review concerns exact source identity, explicit unknowns and failure recovery.

The chosen approach uses Node built-ins to scan JSONL bytes once, hash complete files, reject malformed/truncated/oversized rows and retain compact ID/offset/length/digest entries. One row is read synchronously by offset when the existing synchronous registry getters need it, with file identity and row-digest checks. No persisted second index/schema or new runtime dependency is introduced. An eager cap increase alone leaves the memory problem intact; a database or alternative corpus format expands the agreed delivery boundary.

The APIs remain:

- `validateCorpusDirectory(directory, options)` retains materialized arrays for existing callers. Explicit `indexed: true` selects the bounded indexed representation for registry, publication CLI and staged verifier.
- `writeCorpusCandidate(directory, input, options)` retains existing array input. It also consumes an iterable or an explicit `input.configurationsFile` containing the same configuration JSONL rows, allowing the existing CLI's small input document to reference a large local file. It uses a temporary sorted-offset spool inside its candidate staging directory rather than joining all row strings in memory.
- `createSyntheticRegistry` keeps synchronous `getConfiguration` and `getVin`, its existing history format, and its version/inventory/last-good/active transaction order. File copies stream; immutable history compares retained row digests.
- `registeredCatalogueSources(configurationKey)` still restores only code-owned admitted files. It streams and pins each full source file, retains lookup/offset/digest metadata, and lazily rereads the exact original row for strict source validation and complete envelope equality. Candidate paths, manifest metadata and HTTP callers cannot register sources.

The eager `readCorpusFile` metadata/legacy boundary stays 64 MiB. The streaming production default also starts at 64 MiB. A separately selected bounded resource proof must measure a larger file before any production stream cap is widened. Each streamed row and total row count remain bounded; corruption after activation fails closed on file/row identity and never supplies an altered envelope. No cache is required initially; parsing a single small row keeps the implementation and memory budget clear.
