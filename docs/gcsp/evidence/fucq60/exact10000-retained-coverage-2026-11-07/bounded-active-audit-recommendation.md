# Bounded active verification recommendation

This is a read-only assessment of the current `scripts/gcsp/verify-fleet.mjs` in Mike's `DEV-2026-11-04-036` worktree and the retained `.10` HTTP chunk proof. No verifier tests, source calls, active-store mutations or frozen-pin edits were performed for this assessment. The parent reports that the `.11` full strict active verifier exceeded its 300-second bound without a progress checkpoint, and was stopped/joined with cleanup. That run is uncompleted validation, not a pass.

## Why the current command remains unbounded by its sample argument

`verifyActiveFleet` creates all configuration requests, then all VIN requests and supplied stock requests (lines 194–196). It always resolves both the direct lookup and consuming application port for **every request** in lines 198–211. `sampleSize` only bounds the later HTTP sample (lines 218–220); setting it to one cannot shorten the direct/consumer phase. There is no request-offset, request-limit or progress callback/receipt option.

Setup validates the whole corpus three times: `registry.load()`, `verifyStagedFleet()` and the subsequent `validateCorpusDirectory()` (lines 179–187). Chunking only the request loop would still repeat these full-corpus prerequisites for each invocation. The observed timeout alone does not prove which prerequisite or request dominated; no timing profiler was run.

The strict `matchesRetained` helper (lines 120–144) checks more than HTTP parity: retained source identity, snapshot/dates/references/unknown fields, complete selected options, exact catalogue facts, associated images, synthetic/unknown/source labels and offline routing. The current five-argument helper accepts the exact registered technical supplement and compares merged catalogue/supplement facts; the older four-argument version in the `032` worktree must not be substituted. Its consumer check requires equal status and every returned consuming field to equal the direct result.

## Existing bounded proof and its gap

`docs/gcsp/evidence/fucq62/fleet-dot10-4666-proof-plan/http-chunk.mjs` already selects an exact contiguous 1,024-request range from the same ordered configuration/VIN list, runs direct + consumer + real loopback HTTP for each request, writes progress every 64 requests, retains consumer failures, enforces manifest/egress pins and closes its server. Its summary proves an exact request-key union and no duplicates. It preserves native stock scope as unrun.

However, `directPassed` in that proof checks only direct status, manifest digest and requested kind/ID. HTTP equality plus those checks does **not** reproduce `matchesRetained`: the same wrong technical fact, omitted unknown, source field, image association or label could appear in both direct and HTTP results. The old proof also reconciles totals against an independently completed unbounded strict audit; the timed-out `.11` strict audit cannot supply that reconciliation.

## Minimal delivery change recommended

Reuse the existing bounded HTTP proof with the strict retained assertion shared from the verifier. Export the current five-argument `matchesRetained` unchanged from `verify-fleet.mjs`, and call it for each chunk's direct result with the exact retained configuration record, deduplicated retained image associations, frozen manifest digest and exact supplement. Keep the existing requested-ID/kind checks, consuming-port equality, HTTP status/body parity, progress, timeouts and failure retention. This needs no change to the product flow, corpus, registry, verifier defaults or acceptance criteria.

The exact input assembly is the current strict loop's assembly: find the record in `checked.corpus.configurations` by `direct.identity.configurationId`; union `record.imageIds` and the checked image table's associations for that configuration, preserve order and resolve each through `checked.corpus.images`; find the supplement in `checked.manifest.technicalSupplements` by the same configuration ID. Call `matchesRetained(direct, record, images, frozenManifestDigest, supplement)`. Never derive the expected facts or images from the direct DTO being checked.

A narrow meaningful regression can use the existing small `sourceBackedInput` fixture and actual `vehicleEvidenceDetails` to create the baseline DTO. Require the baseline and exact supplemented DTO to pass. Then change an observed technical value, source identity, image association, unknown label or offline routing and require rejection. Pin the helper's original function body and prove that only its export keyword changes; this gives extraction parity without an unchanged full-suite replay. The parent has selected 1,024-request chunks for proof12; no export or test was executed by this assessment because candidate12 initially pins the existing script.

Run staged semantic validation once for the final frozen manifest. Enumerate the exact configuration + VIN + explicitly supplied stock request list once and seal its ordered request keys/hash. The planned final candidate has 10,001 configuration references plus one VIN reference, or **10,002 requests**; validate that count against the actual sealed candidate rather than infer it from the source count. Select contiguous bounded ranges of at most 1,024 requests. Record exact start/end/count, request-key set, completed entries, manifest/code/input/environment identity, direct/consumer/HTTP errors, offline egress and cleanup in each receipt. If a chunk fails or times out, preserve its exact progress and resume only its uncompleted keys under matching identities; do not replay completed chunks.

The final summary must prove that successful and failed observation keys together cover the expected request list exactly once, all chunk pins match, every started process/server is joined/closed, and no source/external calls occurred. Report real direct, consumer and HTTP error counts separately. Existing deferred consumer defects remain failed observations; the aggregate must not convert them into a `verified-active` result or acceptance. Native current-run stock proof remains unrun unless explicit repository/context/order UUIDs are included.

This is evidence-equivalent to the retained assertions and supplied direct/consumer/HTTP request scope when every enumerated request is covered. It is not permission to rename a partial range `all-records`, ignore a failed observation, infer stock proof, or claim source acceptance. Keep the existing unbounded verifier result recorded as incomplete and link the completed bounded receipts instead.

If a production CLI range is preferred, the smallest safe interface is explicit nonnegative `requestOffset` plus positive bounded `requestLimit`, applied after the immutable full request list is built. It must return `audit.scope = 'request-range'`, exact total/start/end/request-key hash and `targetMet = false` for an incomplete range; only an external exact-union aggregator can claim the completed request scope. Add per-request or small-batch progress with real retained failure counts. This is a larger change than sharing the existing assertion with the already bounded proof, so it is not required for the current delivery path.
