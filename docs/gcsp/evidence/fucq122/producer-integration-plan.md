## Actual service and controller boundary

Use one actual `createGcspRuntime` instance and its `buildServer` dependencies,
repository, PolicyService, DemoClock and trusted identity adapter. FUCQ-100 owns
the central runtime/server composition. The candidate must supply one release
service and one case service on those same objects, register release work before
the clock seals, and preserve existing manual/buddy/notification startup. Do not
spread prototype instances into replacement service objects or introduce a
second case/release runtime inside the harness.

Release is appearance on the provider's next pull, driven through its registered
`stock-release` / `release-pull` clock handler. The resulting stock and tranche
receipt must be read through the actual canonical released-stock port. Case
options and updates must evaluate that exact order UUID and current persisted
employee/contract/driver. Use FUCQ-100's central eligibility lane; do not author
another manual-facts helper, persist a derived eligibility cache, inject known
true, or override policy/scoring to force a recommendation.

The HTTP chunk uses one explicitly owned ephemeral `127.0.0.1` listener, genuine
presenter/employee/Greg sessions, actual registered routes and
`createCaseHttpAdapter`. Mount the actual `mountHelpBody` and `mountCaseQueue`
controllers in JSDOM; enter values and activate their existing review/confirm
controls. Network wrappers may attach the correct session cookie/origin to real
loopback requests and record bounded safe outcomes. They must not manufacture
responses, bypass the identity boundary or replace controller actions with direct
service success. Assert the persisted readback and actual POST outcome, not only
rendered copy. JSDOM controller proof does not establish browser/native-control,
visual or delivered dashboard-host acceptance.

## Input and reset requirements

The retained FUCQ-92 fixture inputs have label-only facts, legacy visibility and
no source expiry. They are useful incomplete-evidence inputs, not suitable-car
proof. A reviewed positive source profile must supply normalized exact snapshot
facts/provenance, valid configuration identity, canonical visibility and a
source-owned `availableUntil` before the actual pull. Its synthetic status must be
explicit. Bind its exact identities and versioned windows to the current run and
central policy/clock; keep the profile small and use actual preparation/input
services rather than inserting released stock.

The FUCQ-100 bootstrap seeds `unreleased` rows containing synthetic identity
metadata. FUCQ-92 `stock/index.js:99` promotes a known row by changing its release
state only, preserving facts. A source appearance therefore cannot silently
replace that existing metadata with normalized vehicle facts. The combined source
plan must identify the actual input/normalization producer revision or an agreed
unseen exact-source identity route. Do not patch known facts after release or
claim a test-authored alternative row is the default scenario's working source.

`createSyntheticStockProvider` closes over `runId` and rejects a pull for another
run. `DemoClock.reset` creates fresh employee/slot/stock identities while retaining
the clock instance and registered handlers; it does not itself rebind that source
provider or seed manual records. The FUCQ-100 candidate must specify how a
registered release handler gets the current run's source profile after reset,
without duplicate handler registration or historical plan reuse. New employee
preparation and genuine new-run sessions must use the same actual runtime APIs.
Reset must not be hidden by constructing a replacement test runtime.
