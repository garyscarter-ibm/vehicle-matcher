acceptance:
- [ ] Every configured live user has a fictional first name, surname and unique email under gcsp-demo.com. Emails identify stable existing employee IDs, preserving saved records.
- [ ] Login uses an injected authentication adapter. The demo implementation checks email/password and returns a configured principal; application routes receive only server-owned identity/roles.
- [ ] Successful login establishes an HttpOnly cookie and appropriate employee or Greg landing page. Invalid credentials, missing input, pending and service failure states are usable and disclose no credentials.
- [ ] The live site uses the signed-in user's stored account, current vehicle, allowance, preferences, offers and ordering state throughout navigation/reload; switching between users shows no former user's cached state.
- [ ] Logout revokes the server session and clears authentication cookies, returns to login and prevents old cookies or browser history from reopening protected data. Saved user information remains for later login.
- [ ] Hosted live entry does not silently impersonate Paula or issue presenter authority. The separate presenter page remains accessible without employee login; its controls remain outside this Story's redesign.
- [ ] Hosted deployment uses PostgreSQL with no silent memory fallback. Account, preference and active run state survive actual runtime reconstruction; missing database configuration is an explicit startup failure.
- [ ] Browser checks at desktop and narrow widths cover login, validation, signed-in identity, logout and long email/name; independent substantive visual/usability critique is addressed and corrected result inspected.
