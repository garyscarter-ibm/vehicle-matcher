goal:
  As the demo owner, I want the scheme's synthetic stock to behave like real BMW UK new stock, so lead times, model mix and colour mix look right to BMW people watching.

  Context:

  Gary decided on 4 November that real configurations come from the sibling story, "Collect a demo set of real BMW configurations for the scheme models" (FUCQ-77). Stock on top of them is synthetic, shaped by aggregate figures from BMW's public new-car stock locator. The locator returns real UK stock as JSON with no key, but carries no option codes (`docs/gcsp/bmw-interface-research.md`, follow-up "real data for the demo", and `docs/gcsp/evidence/fucq-4/stock-locator-2026-11-04.json`).

  This story takes over FUCQ-62's sentence "a seeded synthetic stock generator writes order references … into the Postgres stock table". FUCQ-62 keeps corpus publication.
acceptance:
- [ ] **Sampling.** An explicit, offline-by-default script samples the stock locator for each scheme model line in the FUCQ-77 demo plan.
  It uses at most 400 requests at concurrency 1, and stops on 403 or 429.
  It keeps **aggregates only**, per model line: car count, colour shares, upholstery shares, the lead-time distribution (min and max weeks), delivery-date spread and the price band.
  It never stores an order number, VIN, encrypted VIN, dealer ID, image URL or any single car's record.
  The output is committed as `docs/gcsp/evidence/fucq-20/stock-aggregates-<date>.json`, with the sample date and request count.
- [ ] **Assumptions source.** The aggregates enter FUCQ-82's reviewed seed file as keyed entries, each with its basis, source, date and status `observed aggregate`; this story adds entries to that file and does not create a second loader or source. The following come from `docs/gcsp/background.md` as keyed `assumed` entries:
  release cadence: Monday, Wednesday and Friday, with Monday at 11:30;
  weekly release volume: 300 to 400 cars.
  The generator reads these keys only through FUCQ-82's PolicyService, and where a key overlaps one FUCQ-82 already holds (release sizes, lead times) it uses that key rather than a copy.
- [ ] **Generation.** A seeded generator creates each demo run's stock through FUCQ-81's stock repository port, so the stock lives in the PostgreSQL tables that FUCQ-81 migrates (its in-memory double in unit tests).
  Each car has an `orderUuid`, a 7-digit `orderNumber` and an 8-digit `wholesalerOrderId` (FUCQ-53 allocator), the `configurationId` of a FUCQ-77 configuration, a stock account, a status, a release window and a confirmed delivery week.
  Model and colour shares come from the aggregates, by weighting which configurations receive cars.
  Each car's lead time is drawn from its model line's observed range.
  The same seed and policy version give identical stock. Stock is scoped by `runId`, and regenerating one run leaves other runs and the corpus unchanged.
  The generator is exported as a run-scoped function, `generateStock(runId, seed, policyVersion)`, which FUCQ-85's reset calls. This story does not implement reset, and it does not call FUCQ-85.
- [ ] **Labels.** Every stock car carries `identityKind: synthetic`. Its order identifiers are fictional and never submitted anywhere.
- [ ] **One-place change.** Changing one aggregate entry in the seed file (for example an i5 Touring lead time) and publishing it as a new policy version changes the next generated run consistently, and earlier runs keep their recorded policy version (`docs/gcsp/build-rules.md`, acceptance).
- [ ] **Generator report.** A summary per run states the cars per model line, the colour shares and the lead-time distribution, next to the observed aggregates. Planned and actual shares agree within 5 percentage points for any model line with 20 or more cars.
