goal: As the team, we want the static frontend and the API split the way the product will be (an EDS block on the brand domain, with the API on a subdomain), with sign-in working in every browser.
acceptance:
- [ ] The HLD (`docs/design/gcsp-high-level-design.md`) records the rule: the pages and the API must be same-site (a shared registrable domain) or same-origin (one host, or a proxy), because sessions use cookies. `docs/gcsp/render-postgres-setup.md` records it too.
- [ ] Pick one option and record why:
  (a) a custom domain for both services, for example `gcsp.<domain>` and `api.gcsp.<domain>`, with `SameSite=Lax` cookies and CORS limited to the site origin;
  (b) `gcsp-site` forwards `/api/*` to `gcsp-api`, if Render's static rewrites support an external destination (verify first);
  (c) keep same-origin serving from `gcsp-api`, and retire the live pages from `gcsp-site`.
- [ ] For (a) or (b): the live pages are served from `gcsp-site` again. The redirect routes in `render.gcsp.yaml` and the page serving in `server/gcsp/host.js` are removed or reduced. Sign-in, presenter controls, Paula's offer and Greg's dashboard pass a browser check in Safari, Chrome and Firefox, including a private window.
- [ ] Cookies stay HttpOnly and Secure, browser-supplied ids are still ignored, and the `DEMO_ACCESS_KEY` gate still applies.
out_of_scope: Anything before the 12 Nov demo. Production EDS integration.
