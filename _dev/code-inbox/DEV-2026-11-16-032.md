  Severity: High. The presenter's "Release tomorrow's cars" is slow on stage on the hosted demo.

  **Cause.** The hosted service runs `GCSP_REPOSITORY_MODE=postgres` (`render.gcsp.yaml`). FUCQ-302 removed the whole-state copy from `memory.js` only. `server/gcsp/repository/postgres.js` `run()` still, on every read and transaction, ran `structuredClone` on the cached run snapshot (about 4,000 rows), hashed every row in `flush` with `inputDigest`, and cloned again after commit. One release makes 257 repository calls.

  **Evidence** (local PostgreSQL 16, offline host built as `startHostedGcsp` builds it, vehicle evidence ready, after Start again, 100 cars released):

  * Release tick: 11.5 s, then 14.2 s on the second release. Memory mode: 0.20 s.
  * CPU profile: `postgres.js run()` 87% inclusive (`structuredClone` 59% self, `flush` 28%), 4% idle. So it is CPU cost per call, not database latency.
  * Console readback after the tick (controls, orders, latest release): 2.1 to 3.4 s.
  * In the browser at 1280: click to tiles painted 12.8 s.

  **Fix** (Gary approved, 11 Nov): seal the cached snapshot (deep-frozen, shared) and pass it to reads directly; transactions get fresh table arrays over the same frozen rows; `flush` skips rows that are the same object and digests only replaced rows. `postgres.js` only.

  **Result, same harness:** release 0.82 s, then 1.00 s; readback 0.10 s; Start again 1.4 s (was 5.7 s); outcomes unchanged (100 cars, all 12 handlers ok, same response sizes).

  **Tests** (scratch PostgreSQL): `gcsp-repository-contract` 97 pass, 3 fail (the F71 "ordering new-process readback" check and its two parents, identical on the base); `gcsp-login-postgres` plus 7 other Postgres-related files 132 pass, 1 fail (`gcsp-manual-claims` "concurrent draft edits ... transactional revalidation", identical on the base, memory mode). Both failures are pre-existing.

  **Not measured:** hosted timing (no demo key, and no release run on the shared instance). On Render the roughly 1,000 database round trips per release are now the main remaining cost.

  Related: FUCQ-302 (memory fix), FUCQ-177 (earlier PostgreSQL speed-up), FUCQ-305 (readback size), FUCQ-376 (start-up corpus stall, separate).
