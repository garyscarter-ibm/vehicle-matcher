goal: As Paula, I want my current car's return planned in its own right, so that I know when I hand it back and I keep it until the new one is actually mine.
acceptance:
- [ ] **Separate return plan:** a replacement order has a return plan for the current car, linked to the old contract and vehicle slot FUCQ-71 recorded, and separate from the new car's handover appointment. A new order (no current car) has none.
- [ ] **Return states:** the plan moves through not planned, return requested and return scheduled. It records the return location, a separate appointment through FUCQ-114's port, demo-clock time and provider reference. Requested is never shown as scheduled. Returned/missed outcomes move to FUCQ-168.
- [ ] **Same-visit or separate:** Paula can ask to return the old car at the new car's handover or at a separate slot. The choice and its rules are PolicyService keys, labelled synthetic assumptions.
- [ ] **Current-car relationship:** acceptance, approval, a requested slot and a scheduled handover or return never change Paula's current car. A test proves her current-car identity remains unchanged throughout this planning scope. Only later confirmed completion/return may change it, implemented in FUCQ-168.
- [ ] **Return mileage:** the plan carries the return mileage FUCQ-70 captured, read-only, as recorded at selection.
- [ ] **Read model and routes:** `/api/gcsp` routes read the return plan and request a return slot, using FUCQ-84's server-owned context. Another employee's plan is refused, and browser-supplied employee or run IDs are ignored.
