  About 95 s to start, and about 2 min per tick.

  Diagnosis (hypothesis, to confirm):

  Each database call is a network round trip of about 25 ms. Start-up and the tick handlers make thousands of them one after another, for example per-row reads and writes in loops, instead of batching. The next check is to count queries per tick and per start-up, and find the hot loops.

  Repair acceptance:

  * Count the queries and time start-up and a Next release tick in postgres mode against Render, before and after the fix.
  * Batch or set-base the hot paths, so start-up and a tick each take under about 10 s against Render. Data and behaviour stay the same.
  * Memory mode is unchanged. The repository contract tests pass in both modes.

  Fallback (Gary, 7 Nov):

  If postgres mode is still too slow after the fix, the demo runs in memory mode (`GCSP_REPOSITORY_MODE=memory`).
