  diagnosis 1: reproduction FUCQ-171 screenshot 02 and README observation 4; cause confirmed: seed `lifecycle.appointments.outcomes.v1` `states.completed.owner: employee`, read by AppointmentService (lifecycle/appointments/index.js:142) and drawn by order-progress-body ownerRows through itemOwner.employee = "You". Basis: gcsp-poc 90f8d06b.
  diagnosis 2: reproduction README observation 6 (3 console 403s, T6 demo-paula acting cookie only). Cause confirmed: portalShell mounts presenter controls on every page and refreshState calls GET /api/gcsp/presenter/controls first; identity/http.js:54 answers 403 when the gcsp_presenter cookie is missing. The client already hides the strip silently, but the browser logs the 403 itself, so only skipping the request removes it. The acting context cannot decide (a presenter acting as Paula keeps employee roles only, per shared-contracts identity section), so the server adds an envelope boolean to GET /api/gcsp/context saying whether a presenter control cookie accompanies the request; the client skips the controls read only when it is false. Presenter authority is still checked by every presenter route. Basis: gcsp-poc 90f8d06b.
  diagnosis 3: presentation-only. Reproduction screenshots 375-06/08/10 and observation 7. Cause confirmed: gcsp-case-queue.css forces `.gcsp-table { min-width: 1050px }` and the queue does not use dataTable's existing `stack` option (FUCQ-235); the picker option joins name, status and deadline. Case data is correct (all fields present in the DOM). Shared component: dataTable unchanged.

The copy lives in the client, so the fix is there. Server state (status resolved, confirmation recorded) is correct.
