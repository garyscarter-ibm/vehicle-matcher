goal: As the presenter, I want to move demo time forward on purpose and start a clean run whenever I need to, so that releases, expiries and second offers happen on cue and an old email link can never act on the new run.
acceptance:
- [x] **Demo clock:** a `DemoClock` port (interface in `docs/gcsp/shared-contracts.md`), stored per run in the repository. Every GCSP service reads time through it, never `Date.now()` directly. Tests inject it.
- [x] **Advance:** the presenter can advance time by a step or to a named time, using the presenter role from FUCQ-84.
- [x] **Ticks:** each tick has an event ID, and replaying the same tick ID is a no-op that returns the original outcome. A tick runs the registered handlers in a fixed, recorded order, including:
  release (stock appearing on the next pull, per the round-1 finding);
  hold and offer expiry;
  reconciliation of pending operations.
  This story provides the registry and an ordering test. Each handler is registered by the story that owns it: FUCQ-66 for manual expiry, and the later buddy, release and offer Epics.
- [x] **Startup:** backend startup runs reconciliation once, so outstanding work recovers without a browser. Nothing claims unattended scheduling on a sleeping host.
- [x] **Reset:** reset is a presenter-only operation. It creates a new `runId` and makes it current. It regenerates the synthetic order identifiers (`orderUuid`, `orderNumber`) and the employee state from the versioned fixtures, and restores the clock to the scenario's start.
  It does not touch the immutable corpus (configurations and images) or any operational provider. The previous run's rows stay as history and can't be acted on.
- [x] **Stale-run guard:** after a reset, the old run's offer reads, decision commands and outbox jobs are refused or no-op as stale. A test proves an old offer ID and an old outbox job cannot change the new run.
- [x] **Read-back:** the current run ID, clock time and last tick outcome are readable by the presenter.
