goal: As Russell, I want to start any named scenario from a known state with one reset, so that I can try a journey, see what happens and try it again exactly the same way.
acceptance:
- [x] **Scenario catalogue:** a machine-readable catalogue (shape in `docs/gcsp/shared-contracts.md`) lists each scenario with:
  a stable ID and name;
  the Epics and Stories it exercises, and the capabilities it needs;
  the acting roles, with principals from FUCQ-84's fixtures;
  its start-state fixture version and policy version;
  its clock start, and the tick and release steps it uses.
  The first entries are the main successful journey (FUCQ-109) and the five difficult cases in FUCQ-75.
- [x] **Reset into a scenario:** a presenter-only operation resets into a named scenario by calling FUCQ-85's reset with that scenario's fixture set. It adds no reset of its own: a new `runId`, regenerated identifiers, the clock at the scenario's start and the old run made stale all come from FUCQ-85.
- [x] **Fixtures through the real services:** scenario start states are versioned fixtures (briefs, principals, stock tranches, pending operations) loaded through the same repository and services the application uses. A fixture never sets a predetermined winner or replaces screen text. Runtime values come from PolicyService, and a scenario may name an alternative policy version but keeps no separate defaults.
- [x] **Capability check:** resetting into a scenario whose required capabilities are not built yet returns a clear "not available yet" outcome listing what is missing, rather than a half-built state.
- [x] **Observation record:** `docs/gcsp/manual-acceptance-scenarios.md` gains the per-scenario format: start state, reset and tick steps, short click-through, expected visible result and state change, provisional assumptions, and a dated observations table recording the run ID, build commit, result and feedback.
- [x] **Read-back:** the presenter can read the catalogue, the current scenario, its run ID and its fixture version.
