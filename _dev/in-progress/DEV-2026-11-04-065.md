goal: As Greg, and as every consumer of policy, I want policy versions held as dated rows, so that a published change governs new work while pinned offers and past calculations stay explainable.
acceptance:
- [x] An additive migration (FUCQ-81's runner) creates dated policy tables matching FUCQ-82's seed shape: scheme-rule links, include/exclude rules, the per-scheme price plan, the company/grade allowance and keyed assumptions. Each row carries a policy version and an effective-from date.
- [x] Seeding loads the reviewed repo seed into the tables idempotently: re-running it creates no duplicate version. The seed file stays the reviewed origin of version 1.
- [x] A PostgreSQL-backed provider sits behind the same `PolicyService` interface as FUCQ-82's file provider. With `GCSP_DATABASE_URL` set, the service reads the active version from the tables. Consumers and their tests change nothing.
- [x] A `publishPolicyVersion` operation writes a new dated version from a validated change set and records who published it and when. The previous version is never mutated. Publishing requires a principal with the Greg role, which the route layer enforces once FUCQ-84 is in. This story exposes it as a service operation, plus a test.
- [x] A read can name a pinned version: it returns that version's values rather than the active ones, so a held offer is not silently repriced (HLD invariant). An effective date in the future does not govern current reads until the demo clock reaches it. The clock is injected; FUCQ-85 supplies the presenter clock.
- [x] Tests prove:
  one published entry changes the affected reads for new work;
  a pinned read returns the old value;
  an invalid change set is rejected without writing;
  the in-memory and PostgreSQL providers agree.
