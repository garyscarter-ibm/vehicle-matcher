  **Likely cause:** the test connects to `localhost`, which resolves to IPv6 `::1`, while the server it starts listens elsewhere (for example on 127.0.0.1), or it isn't ready yet. Under load, the IPv6 attempt times out before the fallback.

  **Impact:** a red critical path hides real regressions. Every merge today needed reruns to tell this flake apart from a real failure.

- diagnosis: `startGcspDemo` calls `server.listen(port, 'localhost')`; on this Mac `localhost` resolves to `::1` first, so the server binds `::1` only. The test client (`server/test/helpers/local-https.js`) used Node's default `autoSelectFamily` (happy eyeballs) with a 500 ms per-attempt timer. Server and client share one event loop, so when allocation work blocked it past 500 ms the `::1` attempt timer fired first (ETIMEDOUT `::1`), the fallback to `127.0.0.1` found no listener (ECONNREFUSED), giving the reported AggregateError. Not a listen race: `startGcspDemo` awaits `listen` before returning. Basis: gcsp-poc 5b51a675, Node 26.5.0.
- repair: the helper's request sets `autoSelectFamily: false`, so it connects to the same first lookup address the server took, with only the request's own timeout. All 14 files using `createLocalHttpsFixture` get the fix; no other test helper connects to localhost. Production launcher binding unchanged (browsers do their own fallback).
- regression: `server/test/local-https-helper.test.js` starts an HTTPS server on `localhost`, hooks `dns.lookup` to block the loop 1.5 s right after the connect starts, and expects a 200.
