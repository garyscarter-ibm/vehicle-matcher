goal: As Paula, I want to say what I prefer, how much each preference matters and what I must have, and see straight away which cars that would favour and why, so that I can trust the buddy with my brief.
acceptance:
- [x] **Brief screen:** a brief screen in a GCSP block under `blocks/gcsp/`, inside FUCQ-64's shell. It has a preference slider per dimension, with a separate importance or indifference control next to each. Comfort and sportiness can both be high, with no forced opposites.
- [x] **Essentials and known facts:** essentials (carrying, equipment, charging readiness) are confirmed as separate yes, no or unknown answers. Known facts (current car, driver, contract) are prefilled from server context and editable only where the server allows. There is no contribution or cash question (Q16).
- [x] **Live preview:** a debounced live preview calls FUCQ-29's read-only recommendation endpoint and shows the top cars, each with grounded reasons and trade-offs. It covers loading, zero eligible, essential-unknown and unavailable states; a stale response never overwrites a newer one.
- [x] **Save and consent:** Save confirms the brief through FUCQ-91 and shows the new version. A separate, clear consent control switches the buddy on to search and hold. A version conflict shows a refresh prompt and keeps the user's edits.
- [x] **Shared kit:** the screen is built from the shared kit per `COMPONENTS.md`. New or extended components go into the kit, the catalogue and the gallery in the same commit. The ratchet baseline only falls.
- [x] **Embeddable (Q18):** the block also mounts as a custom element, with no inline scripts, inline event handlers, `eval`, `new Function` or string timers.
- [x] **Accessibility:** keyboard operable throughout, visible focus, labelled sliders with value readouts, reduced-motion support, and layouts that cope with long model names and missing images.
