goal:
  ## What happens

  In the Java API (services/gcsp-api), a signed-in principal's run scope comes from the `GCSP_RUN_ID` configuration, not from the environment's active run.

  FUCQ-479 lets the presenter reset the run, which creates a new active run. After a reset, employee and Greg requests are still scoped to the configured run id. They then see the old run's state, or none at all, instead of the fresh one.

  ## Impact

  This blocks the demo flow where the presenter resets and then a journey starts. It does not affect a deployment that never resets.

  ## Expected

  The principal's RunContext resolves to the environment's active run, read from the run table inside the request's transaction. This matches the "active run" wording already used by OfferRecords (FUCQ-465).

  ## Found

  Found in the independent review of FUCQ-479 (DEV-2026-11-13-047, merged ccc6acd1a on gcsp-poc-dev, 2026-11-14). It has not been reproduced on the hosted dev build.
