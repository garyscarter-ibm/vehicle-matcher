# GCSP TransactionRepository

Implements shared contract 1.0.0. Import the backend factories and helpers from `index.js`.
The retail HTTP server does not open this repository or require database configuration.

```js
import { createPostgresRepository, inputDigest } from './index.js';

const repository = createPostgresRepository();
const startup = await repository.open();
// Inspect startup.status, then startup.value.migrationStatus.current before enabling GCSP writes.
const outcome = await repository.transaction(context, {
  commandId: stableCommandId,
  inputDigest: inputDigest(commandInput),
}, async (tx) => {
  const claim = await tx.conditionalClaim(commandInput);
  if (claim.status !== 'ok') return claim;
  const offer = await tx.insert('offers', offerRow);
  if (offer.status !== 'ok') return offer;
  return tx.enqueueNotification(notificationJob);
});
await repository.close();
```

`GCSP_DATABASE_URL` is backend-only. No configuration, raw driver error or connection string appears in a returned outcome. A connection failure returns `unavailable`; it never switches providers. Startup applies migrations by default. `{ migrate: false }` reports pending versions without applying them. A backend-only `schema` option supports isolated test schemas; it accepts a simple lowercase SQL identifier. Tests may inject a pool that they own and close.

For unit tests, explicitly create a store with `createMemoryStore()` and inject it into `createMemoryRepository({ store })`. Reopening another handle against that store retains state; it is not durable storage across process restarts. PostgreSQL is the durable provider. Both use the same validated transaction engine. Reads and writes are run-bound; a `RowRef.key` includes every primary-key field, including `runId`. Filters and patches accept only the table's registered fields. Business revalidation, role authorization, allocation ranking and expiry decisions remain with consuming services.

Slot rows explicitly configure positive `capacity` and may supply positive `employeeCapacity`. The repository does not invent a policy limit. New conditional claims require `expectedStockVersion`, `expectedSlotVersion`, exact `orderUuid`, `holdId`, `claimId`, employee/slot, `type`, UTC `expiresAt`, `policyVersion` and `quoteId`. They return the hold, claim and new stock/slot versions. Both hold types share uniqueness across active and pending states. Updates use compare-and-swap and cannot revive terminal holds. Consuming services update corresponding hold/claim/stock states together.

Callbacks return a shared outcome and perform no external network effects. A failed mutation poisons the transaction even if the callback ignores its result. A lookup returning `not-found` is an ordinary miss. A thrown callback or malformed success rolls back. Command, event and outbox replays return their original outcome; changed input digests conflict. Use `inputDigest` for canonical JSON digests and keep logical keys stable across retries. An unavailable acknowledgement after COMMIT is uncertain: retry the original command ID and digest to reconcile its stored outcome.

**Mutation journal (FUCQ-422).** A committing `transaction` or `resetRun` hands its backend `{ commit: true, outcome, mutations }`. `mutations` is a frozen array, in first-write order, with one entry per changed row identity: `{ type: 'insert' | 'update', table, key, row, expectedVersion? }`. `key` is the complete primary key (including `runId`), `row` is the final stored row, and for updates only `expectedVersion` and `previous` are the version and row stored before the transaction, for a version-checked write and evidence-reference cleanup. Entries cover automatic insert receipts, the command or reset receipt, every row a composed `conditionalClaim` writes and, for `resetRun`, both the retired run with its stale outbox jobs and the new run's seed. Rolled-back, refused, failed-CAS and replayed attempts carry no journal, and no-op writes add no entry. There is no delete type. Backends may ignore the field. PostgreSQL (FUCQ-423) persists exactly this set and refuses a commit that lacks it: a small write no longer scans or compares the run's tables, and its statements and changed rows stay constant as unrelated history grows (`server/test/gcsp-postgres-write-set.test.js`). Updates keep the `version = expectedVersion` check, and a cache hit derives its committed fingerprint from the locked probe plus the write set.

**Evidence hydration (FUCQ-425).** A PostgreSQL read loads only the shared evidence snapshots its selected rows reference. It does this in sequential batches of at most 500 digests. A size probe first keeps each fetch within `writeBatchBytes` of stored JSON, and a snapshot larger than that travels alone without truncation. A one-snapshot read stays a single query. Row order, legacy inline facts and digest verification are unchanged, and a missing or corrupt snapshot still refuses the whole read (`server/test/gcsp-postgres-evidence.test.js`).

**Scoped receipt transactions (FUCQ-424).** `transaction(context, command, work, { scope: [{ table, key }] })` declares complete primary keys in `event_receipts` or `tick_runs` of the context run; anything else returns `invalid/invalid-scope` before `work` runs. On a cold cache PostgreSQL then loads all runs plus the declared keys, the insert-replay receipts that `insert` consults and the command receipt, in one query, instead of the whole run. If `work` touches anything undeclared (another table, a list, an unlisted key), core raises a scope miss and the backend reruns the same work on the full snapshot inside the same locked transaction, so a partial state never reads as empty. A scoped commit persists the same write set but does not cache the partial state. Declared work must be re-runnable: no effects beyond `tx` (`server/test/gcsp-postgres-scoped-hydration.test.js`). Declared callers: the clock advance, tick start/receipt/finish/interrupt transactions, and the allocation prepare, legacy-cursor, advance and complete receipts. `createStrictScopeRepository` in `server/test/helpers/` proves each declaration completes on its declared state alone.

**Run revisions (FUCQ-421).** Migration `0010_repository_revisions.sql` adds `repository_revisions`: a monotonic `runs` revision and one `run:<id>` revision per run, each advanced at most once per transaction by statement triggers on every foundation table (insert, update, delete, truncate), in the writing transaction. Rolled-back, refused, failed-CAS and replayed attempts write nothing, so they advance nothing; writers outside the adapter are seen too, and the rows cannot be deleted or lowered. With 0010 applied, each read and transaction checks freshness with one primary-key read of those two rows, after the run lock, instead of `count`/`sum(version)` over all foundation tables, so the check stays constant as history grows; a commit caches the probe plus its own bumps, and any concurrent change makes the next probe reload. An instance opened before 0010 is applied (`migrate: false`) keeps the legacy fingerprint, which stays correct alongside upgraded instances. CAS, occupancy and replay still check authoritative rows under the run lock (`server/test/gcsp-postgres-run-revision.test.js`).

**Selected receipt reads (FUCQ-419).** `readReceipts(context, { consumerIds, eventIds?, state?, projection? })` returns this run's `event_receipts` for 1-16 consumers, optionally up to 500 exact event IDs and one exact state, sorted by (consumerId, eventId), with the same context/environment checks as `read`. PostgreSQL answers it with one `event_receipts_pkey` prefix query after the revision probe; named projections in `receipt-projections.js` (`allocation-summary`, `quote-inputs`) run in SQL there and in JavaScript elsewhere, and must stay equal (`gcsp-postgres-receipt-reads.test.js`). Allocation reads producer triggers, completed-history summaries, evaluation slices and attempts through it. No migration or index was added: the primary key covers every predicate.

`0001_transaction_foundation.sql` creates the 17 non-policy foundation tables. Rows use JSONB payloads with generated run/key/version columns, scoped foreign keys, uniqueness constraints and partial indexes for occupying holds/claims. SQL transactions serialize per run and persist only changed rows; native constraints also protect exact-car exclusivity. The append-only migration ledger records filename, version, checksum and applied time. Each numbered file commits with its ledger entry; a changed or missing applied file is refused. Applied migrations must remain unchanged. The six policy table names are reserved for FUCQ-83's `0002_policy_tables.sql` and return `invalid/unsupported-table` until enabled.

Run `node --test server/test/gcsp-repository-contract.test.js` from the worktree root. The same suite runs against both providers when `GCSP_DATABASE_URL` is set, creating and deleting isolated test schemas. A separate live test bypasses the port to prove the native partial uniqueness constraints. Only an unset URL skips these checks; an empty, invalid or unreachable configured URL fails. Driver doubles separately verify failure handling and migration orchestration; they do not prove real SQL execution. UI consumers can use `server/test/fixtures/gcsp-repository-outcomes.json` for unavailable, conflict and stale-version response shapes.
